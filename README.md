# iwagaki

舞鶴市 **吉原**地区を対象に、**同じ高潮水位に対して、地形データを変えると浸水判定が
どこで変わるか**を地物単位で示すプロトタイプ。

公開 viewer: **https://iwagaki-viewer.tonbo.workers.dev**

![H=1.0m での比較](docs/images/flood_compare_H1.0.png)

左 = PLATEAU 5m 地形の浸水域、中 = 0.5m 航空レーザ地形の浸水域、
右 = 差分（赤 = 新たに浸水 / 黄 = 浸水しなくなる）。

---

## 1. 何をするものか

PLATEAU と地形観測を「3D で重ねて見せる」のではなく、**役割を分けて突き合わせる**。

| 役割 | データ | 何を担うか |
|---|---|---|
| semantic city model | PLATEAU（建物・道路） | 地物の**識別子と意味** |
| terrain observation | 0.5m 航空レーザ DEM / 地上点群 | **現況の微地形** |
| derived assertion | 本リポジトリの解析結果 | 地物ごとの地盤高・浸水深・**判定の変化** |

出力は「浸水ハザードマップ」ではない。**「地形データを変えると、どの道路・どの建物で
判定がひっくり返るか」**という差分そのものが成果物である。

### 比較する 4 つの地形条件

| 条件 | 中身 | 何を切り分けるか |
|---|---|---|
| `baseline` | PLATEAU 地形モデル LOD1 TIN（5 m 格子） | 出発点 |
| `highres` | 京都府 数値標高モデル 0.5 m（航空レーザ 2019-2023） | データ源 + 解像度の合計 |
| `control` | `highres` を 5 m に平均集約 | **解像度だけ**を落とした対照 |
| `pointcloud` | `highres` に地上点群（バックパック SLAM 2026-07）の地表面を融合 | 地上観測が足す分 |

`control` があるので「データ源が効いたのか、解像度が効いたのか」を分けられる。

### 手法の要点 — 連結浸水開始水位 `h_conn`

浸水判定を `標高 < 水位` では行わない。**海から連結して到達できるか**を解く。

各セルについて「そのセルが海と連結して浸水し始める最小水位」`h_conn` を 1 度だけ計算する。
すると任意の水位 H について

- 浸水するか = `h_conn ≤ H`
- 浸水深 = `max(0, H − 標高)`

が定数時間で決まる。**水位を動かしてもサーバ往復も再計算も発生しない。**
viewer の水位スライダはこの性質の上に載っている。

モデルは静水位（hydrologically-connected bathtub, Poulter & Halpin 2008 系）で、
越流の時間発展・流量・波の打ち上げは含まない。詳細は `docs/DESIGN.md`。

## 2. 分かったこと

すべて実測値。詳細と限界は `docs/RESULTS.md`。

### 判定は変わる。しかも面積ではなく場所が変わる

水位 **H = 1.0 m T.P.**、PLATEAU 5m → 0.5m DEM:

| | |
|---|---:|
| 判定が変わる地物 | **137 / 905 件（15.1 %）** |
| 浸水面積（PLATEAU 5m） | 124,979 m² |
| 浸水面積（0.5m DEM） | 122,733 m² |
| 新たに浸水 / 浸水しなくなる | 19,378 / 21,624 m² |

**合計面積はほぼ同じでも、陸域 702,033 m² のうち 41,002 m²（5.8 %）で入れ替わる。**

### 主因は解像度ではなくデータ源だった

`|Δh_conn| > 0.25 m` のセル割合で分解する:

| 比較 | 割合 | 意味 |
|---|---:|---|
| PLATEAU 5m → 0.5m DEM | 12.7 % | 合計 |
| PLATEAU 5m → 5m 対照 | **10.5 %** | **データ源の差** |
| 5m 対照 → 0.5m DEM | 3.4 % | 解像度の差 |

当初の見込みは逆だった。**細かくしたから変わったのではなく、元のデータが違うから変わった。**

### 地上点群が足すのは 1 桁小さい

既往最高潮位 T.P.+0.93 m での判定変化:

| 比較 | 判定が変わる地物 |
|---|---:|
| PLATEAU 5m → 0.5m DEM | **95 件** |
| 0.5m DEM → 点群融合 | **18 件** |

**大半の価値は航空レーザ 0.5m DEM の時点で得られている。**
地上点群（4.98 億点 / 20 GB）が足すのは、その上に乗る補正である。

ただし点群が覆えた護岸帯（0.209 ha）に限れば **39.8 % のセルが 10 cm 以上違い**、
点群のほうが低く出る側に裾を引く。内陸側の防護レベル（h_conn の p05）は
0.85 → 0.70 m に下がった。**効く場所は狭いが、効く場所では大きい。**

### 越流開始水位

このモデルが出す「海から連結して内陸が浸水し始める水位」は
**T.P. +0.25 m**（0.5m DEM）。PLATEAU 5m では +0.40 m。
**5 m 地形は護岸天端を削るので、越流を遅く見積もる。**

## 3. 対象範囲

舞鶴市 吉原（東吉原・西吉原、吉原入江周辺）。

| 項目 | 値 |
|---|---|
| AOI | EPSG:6674（JGD2011 / 平面直角座標系 第VI系）で X −61500〜−60500, Y −60500〜−59500 |
| 大きさ | **1000 m × 1000 m** |
| 中心 | 東経 135.32796°, 北緯 35.45731° |
| 標高（0.5m DEM） | 0.00 〜 152.17 m T.P.（中央値 1.80 m） |
| 陸域 / 開放水面 | 702,033 m² / 297,968 m² |
| PLATEAU 地物 | 911 件（うち橋梁・高架など 6 件は地盤高が意味を持たないため解析対象外） |

吉原は二本の水路（吉原入江・伊佐津川）に挟まれた低平な砂州上の漁村集落で、
市街地部の標高は概ね 0.5〜3 m T.P. しかない。
**護岸天端・道路の微かな峰・路地の窪みが浸水の連結性を支配する**地形であり、
5 m 格子ではそれらが平滑化される。微地形が効くことを期待できる典型として選んだ。


## 5. 使い方

### セットアップ

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

外部ツール: GDAL 3.x（CLI）、PDAL 2.x（点群パス）。

### 解析を通す

```bash
scripts/run_all.sh        # 取得 → 地形 → 浸水 → 比較 → 地物結合 → 図
scripts/build_web.sh      # → Web 配信アセット（タイル・3D Tiles・catalog）
```

初回は京都府 DEM タイル 4 枚（各 12 MB）と PLATEAU CityGML 4 メンバー（計 1.25 GB）を取得する。
配布 zip は 3.7〜10.7 GB あるが、**HTTP Range で必要なメンバーだけ**抜くので全体は落とさない。
2 回目以降はキャッシュを使い 1 分程度で完走する。

主な成果物（`data/out/`）:

| ファイル | 内容 |
|---|---|
| `dtm_{baseline,highres,control,pointcloud}_*.tif` | 4 条件の地形 |
| `h_conn_*.tif` | 連結浸水開始水位。**1 枚で全水位を表す** |
| `objects.geojson` / `objects.csv` | 地物 + 条件ごとの地盤高・h_conn |
| `changed_H*.geojson` | 判定が変わった領域 |
| `summary.json` | 設定・指標 |

### 点群を投入する

```bash
scripts/run_pointcloud.sh "/path/to/吉原点群データ"
```

LAS の実態確認 → 被覆・密度の実測 → 京都府 DEM との突き合わせ → 融合地形の生成 →
浸水の再計算 → 地物単位の影響評価 → 表示用 COPC まで通す。
20 GB を数回読むので 30 分程度かかる。

PDAL が開けない LAS があれば、**原本を変更せずに**修復コピーを作って読む
（`scripts/24_repair_las_evlr.py`）。使えなかったファイルは成果物 JSON の
`dropped_files` に必ず残る。

### 配信する

```bash
cd web
npx wrangler login          # 初回のみ
npm run deploy:dry          # 設定の検証だけ（Cloudflare に何も作らない）
npm run deploy              # build → COPC を R2 → Worker をデプロイ
npm run deploy:check <URL>  # Range 206 / 圧縮 / キャッシュを実測して合否を出す
```

静的アセットは Workers Assets、**COPC だけ Worker 経由で R2 から Range 配信**する
（Workers Assets は Range に 200 を返すため）。詳細は `docs/INFRA.md`。
