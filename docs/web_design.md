# WEB_DESIGN — ブラウザ側の設計

解析結果（`docs/design.md` / `docs/results.md`）をブラウザで見せるための設計。
**配信・描画・ネットワークをどう組んであるか**を書く。

実測値は `docs/web_results.md`、Cloudflare の挙動は `docs/platform.md`、
配信の構成と手順は `docs/infra.md`、生きているタスクは `docs/todo.md`。

根拠区分は `docs/data.md` と同じ（**[実測]** / **[既知]** / **[仮説]** / **[未確認]**）。

---

## 層の分け方

依存は上から下への一方向だけ。下の層は上の層を知らない。

```
ui/          controls / inspector / section / perf panel
   ↓
view/        カメラのプリセット、ビューキューブ、測線
   ↓
three/       Viewer（カメラ・投影・描画ループ）、地形 / PLATEAU / 地物 / 点群のメッシュ
   ↓
pointcloud/  index / lod / decode / renderer   （view から差し替えられる）
   ↓
net/         scheduler / range fetch / cache
   ↓
assets/      catalog、タイルのパッキング、PNG 復号
   ↓
domain/      AOI・CRS・水位・地形条件・地物 assertion、wet(H) / depth(H)
```

守るルールは 4 つ。

| ルール | 理由 |
|---|---|
| `domain/` は three / @loaders.gl を **import しない** | ドメインモデルを描画ライブラリの API に縛らない。node でそのままテストできる |
| `net/` は描画を知らない。渡るのは URL・Range・優先度だけ | 取得の制御をレンダラの内部に埋めない |
| レンダラは `fetch` を直接呼ばない。**必要なものを宣言**して結果を受け取る | 3D Tiles も COPC も地形タイルも同じ scheduler を通す |
| `pointcloud/` の 4 要素（index / LOD / decode / render）は個別に差し替えられる | レンダラを替えても他の 3 つを再利用する |

**描画ライブラリに依存しない判断は `domain/` に置く。** レンダラの差し替えが
実際に控えている以上、描画側に分岐を書くと差し替えのたびに書き写して、そのたびに間違える。
`domain/terrain.ts`（surface → どのタイルを使うか）と `domain/camera.ts`
（地図のカメラ → ローカル ENU メートル）はこの理由で純関数として切り出してある。

## ドメインモデル

### 対象範囲は 3 つある

入口は **`data/areas.json`**（範囲の索引）。`domain/areas.ts` がそれを読み、
`?area=<id>` で選ばれた範囲の catalog を取る。**索引が無い配信物では
`data/catalog.json` 1 枚の単一範囲として動く**（旧配信物との互換）。

| 範囲 | 広さ | 条件 | 地物 |
|---|---:|---|---:|
| `yoshiwara` | 100 ha | 4 条件 ＋ 差分 4 本（点群あり） | 1,223 |
| `nishi_maizuru` | 625 ha | `baseline` / `highres` / `diff` | 6,118 |
| `higashi_maizuru` | **1,000 ha** | 同左 | 8,368 |

**範囲を替えるとページごと読み直す**（`?area=` を付けて `location.href`）。
範囲が変わると `local_frame`（ローカル ENU の原点と回転）・タイルの URL・
地物・3D Tiles・既定の視点が**すべて**入れ替わるので、差分で入れ替える経路を
用意すると `main.ts` の組み立てが二重になる。庁内で「範囲を行き来しながら見る」
使い方は聞いていない [未確認]。

範囲によって出せるものが違うので、**画面に出す選択肢は catalog から決める**。

| | 決め方 |
|---|---|
| 地形データの `<select>` | `catalog.terrain` にある条件だけ（`conditionsOf()`）。出すと選んでタイルが 404 になる |
| `点群` のチェック | `catalog.pointcloud.url` があるときだけ（`layersOf()`） |
| `判定差` ボタン | 従来どおり差分タイルの有無。広い 2 範囲では `highres` のときだけ押せる |
| 対象範囲の `<select>` | 索引の範囲が 2 つ以上あるときだけ出す |

#### 起動時の倍率と注視点は範囲の広さで変わる **[実測]**

`INITIAL_ZOOM = 17.2` は 100 ha 用で、**2.5 km 角の範囲では 6 分の 1 しか
見えない**。`initialZoom(catalog)` が AOI の幅から計算する（1 km 四方までは
17.2 をそのまま返す = `docs/web_results.md` の実測値と比較できる状態を保つ）。

**合わせるのは幅だけ。** 高さにも合わせると 15.4 まで引くことになり、
`Math.round(zoom)` が 15 = 粗メッシュのままになる。幅合わせなら 16.1 で
細メッシュに乗る。縦は切れるが、そこはパンとズームで足りる。

注視点は **catalog の `aoi.focus_wgs84`**（標高 5 m 以下の建物の位置の中央値。
`scripts/83` が入れる）。**AOI の矩形の中心ではない** — 625 ha の真ん中は
港と山に落ちて、起動直後の画面に市街が入らなかった [実測]。
点群がある範囲は従来どおり点群の帯の中心を見る（そちらが優先）。

座標を viewer に埋め込まないのは `default_section` と同じ方針で、
**どこを見せるべきかは解析側が知っている**から。

#### 空の辞書を truthy で判定してはいけない **[実測]**

`catalog.default_section` は天端の解析（`scripts/87`）を回していない範囲では
`{}` だった。読み側が `if (ds)` で見ていたので **`{}` を通して `ds.from[0]` で
落ちていた**（広い 2 範囲で実際に落ちた）。直し方は両側で 1 つずつ。

- `scripts/83` は**空なら鍵ごと落とす**
- 読み側は `ds?.from && ds?.to` まで見る

`pointcloud_coverage` も同じ形だった。こちらは**範囲を見ずに
共有ディレクトリのファイルを拾っていた**ので、点群が無い範囲まで
吉原の被覆輪郭を指していた。

### 連結浸水開始水位 `h_conn`

このアプリの構造は `h_conn` を持っていることから決まっている（`docs/design.md`）。

```ts
const wet   = (hConn: MTP, H: MTP) => hConn <= H
const depth = (elev: MTP, hConn: MTP, H: MTP) => (wet(hConn, H) ? Math.max(0, H - elev) : 0)
```

セルごとに「そこが海と連結して浸水し始める最小水位」を 1 枚持つので、
任意の水位 H の判定と浸水深が定数時間で決まる。したがって

- **水位を変えてもサーバ往復も再計算も発生しない。** シェーダの uniform が変わるだけ
- 配信するタイルの枚数が水位の数に依存しない

同じ式を GLSL 側（`view/floodMeshLayer.ts`）にも書いている。
**両者が一致することはテストで守る**（後述）。

### 地形条件と差分

解析が持つ 4 条件と、**4 組の差分**をそのまま配信する。

| surface | 幾何を取るタイル | 色を取るタイル |
|---|---|---|
| `baseline` / `highres` / `control` / `pointcloud` | 同名の条件 | 同じタイル（RGB=標高, A=h_conn） |
| `diff` | `highres` | `diff`（R=h_conn(baseline), G=h_conn(highres), B=標高(baseline)） |
| `diff_src` | `control` | `diff_src`（R=h_conn(baseline), G=h_conn(control), B=標高(baseline)） |
| `diff_res` | `highres` | `diff_res`（R=h_conn(control), G=h_conn(highres), B=標高(control)） |
| `diff_pc` | `pointcloud` | `diff_pc`（R=h_conn(highres), G=h_conn(pointcloud), B=標高(highres)） |

B（出発する側の地盤高）は**単純モデルの判定差**に要る。到達する側の地盤高は
地形タイルの RGB にある。詳細は下の「窪地を別に出すのでは足りなかった」。

差分モードでも地形メッシュは要るので、**幾何は元の条件から取る**。
どちらから取るかは任意ではない。`diff_pc` の形を `highres` から取ると、
「点群で変わった場所」を点群の形の上に描けず、何を見ているのか分からなくなる。

この解決は `domain/terrain.ts` の `resolveSurface()` が持つ。

#### 4 条件は集合ではなく鎖

`README.md` の「切り分けたいもの」列がそのまま構造である。**1 段ごとに 1 要素だけを
変えた連鎖**で、横一列の選択肢ではない。

| 段 | 変えるもの | 到達する条件 |
|---|---|---|
| — | 出発点 | `baseline`（PLATEAU TIN・5 m） |
| 1 | 源だけ替える | `control`（航空レーザ DEM・5 m のまま） |
| 2 | 解像度だけ上げる | `highres`（同じ源・0.5 m） |
| 3 | 観測を足す | `pointcloud`（地上 SLAM の地表面を融合） |

**`control` は「4 つ目の選択肢」ではなく鎖の中の 1 地点である。** 源だけを替えた
地点があるおかげで `baseline` と `highres` の差を「源のせい」と「解像度のせい」に
分けられる。並列に並べるとこの意味が画面から消える（`ui/controls.ts` の
`CONDITIONS` はこの順で並べてある）。

**同時に 2 条件は描けない。** 同じ場所の標高を 4 通りに測ったものなので、
メッシュを 2 枚出すと数十 cm 差で交差する（粗メッシュと細メッシュで
同じ問題を避けているのと同じ理由）。だからチェックボックスではなく 1 つ選ぶ。
**断面図だけは例外**で、線は z-fight しないので複数条件を重ねられる。
`main.ts` の `SECTION_SERIES` は **4 条件すべて**を引く。代償は測線ごとに
条件 1 つぶんタイルを引くことで、実測では起動後の要求が 64 → 67 本、
転送が 4.84 → 4.85 MB（3 タイルぶん）だった。

UI は `<select>` にしてある。ボタン 4 つは 268 px 幅で 2 行に折り返すうえ、
頭には水位も入るので場所が無い。**梯子の順序は option の並びとして残る**ので、
開けば「源を替える → 解像度を上げる → 観測を足す」が読める。
`判定差` だけはボタンのまま隣に置く。**差分タイルが無い条件では押せない**ことを
見せたいので、押せる/押せないが常に見えている必要がある。

#### 比較のペア

判定が変わるかどうかは、常に**ペアに対して**決まる。ペアは
`domain/terrain.ts` の `comparisonPair(surface)` が決める。

| surface | ペア |
|---|---|
| `diff` / `diff_pc` | その差分タイルが持つ 2 条件 |
| `control` / `highres` / `pointcloud` | `baseline` 対 その条件 |
| `baseline` | 自分対自分（判定は常に「変わらない」） |

以前は `domain/flood.ts` の `decisionChanged()` / `changeBand()` が
baseline と highres を**ハードコード**していた。呼び側は
インスペクタと `semanticsMesh.setStyle()`（地物の赤 + `changedOnly` のフィルタ）で、
結果として **`diff_pc` を選んでいても赤い地物は 5m↔0.5m のまま**だった。
地形の色と地物の色が同じ画面で別の比較を示していたので、ペアを引数にした。

既定は `surface: 'highres'` なので既定のペアは `(baseline, highres)` で、
以前のハードコードと同じ組である（`docs/results.md` の件数と整合する）。

**差分は鎖の辺として 4 本焼いてある** [実測]。

| 差分 | 辺 | 切り分けるもの | 枚数 / 容量 |
|---|---|---|---|
| `diff_src` | baseline → control | **データ源だけ**（どちらも 5 m 格子） | 131 / 0.21 MB |
| `diff_res` | control → highres | **解像度だけ**（どちらも航空レーザ源） | 131 / 0.58 MB |
| `diff_pc` | highres → pointcloud | 地上観測が足した分 | 131 / 0.63 MB |
| `diff` | baseline → highres | 上 2 段をまとめたもの | 131 / 0.57 MB |

`ui/controls.ts` の `DIFF_OF` が `判定差` ボタンに割り当てるのは
`control → diff_src` / `highres → diff` / `pointcloud → diff_pc` の 3 つ。
**`diff_res` は載せていない。** `highres` に割り当てると「0.5m の判定差」の意味が
合計 12.7 % から解像度だけの 3.4 % に変わり、`README.md` と `docs/results.md` の
見出しと食い違うため。`__iwagaki.setSurface('diff_res')` で触れる。

### 鉛直基準 **[実測]**

PLATEAU 3D Tiles は**楕円体高**、解析はすべて**標高 T.P.**。
差はジオイド高 N で、AOI 中心で **36.955 m**（PROJ 経由、GSIGEO2011）。
`catalog.json` の `vertical.geoid_undulation_m` に焼いてある。

**我々のレイヤ側を `z_render = z_TP + N` で持ち上げる。** 3D Tiles 側の行列は触らない。

## 描画層を自前で持つ

描画は three.js だけで組む。**ベースマップは 1 枚も描かない**（背景は単色）ので、
地図ライブラリが要る理由が「カメラ・投影・操作・ギズモ」の 4 つしか無かった。

| | 実体 |
|---|---|
| カメラ・投影・操作・描画ループ | `three/viewer.ts`（`Viewer`）。透視と正射を持つ |
| 地形・浸水・差分 | `three/terrainTiles.ts` + `three/floodMaterial.ts` |
| PLATEAU 建物 | `three/plateauTiles.ts`（b3dm のパースは `@loaders.gl/3d-tiles`） |
| 地物ポリゴン・点群被覆 | `three/semanticsMesh.ts`（picking も） |
| 点群 | `three/pointsRenderer.ts`（`Points` 1 つ / ノード） |

前身は MapLibre GL JS + deck.gl（`MapboxOverlay`, interleaved）だった。
外した理由は 1 つで、**初期チャンクの約 1/3 が MapLibre だったから**である
（`docs/web_results.md`「初期チャンクの内訳」）。細い回線で効くのはここしかない。
判断の経緯は `docs/adr/2026-08-23-three-js.md`。

### ズームの規約 **[実測]**

`Viewer.getZoom()` / `setZoom()` は **タイル 1 枚 = 256 px 基準**。
`Math.round(getZoom())` がそのまま要求するタイルの z になるように選んである。

**MapLibre の `getZoom()` は 512 px 基準で、同じ景色でも値が 1 小さい。**
移行直後にこれを取り違えていて、`INITIAL_ZOOM` に MapLibre の 15.6 をそのまま
渡していた。実測で m/px が 1.282 対 2.567（ちょうど 2 倍）、可視範囲が 4 倍、
要求するタイルが z17 25 枚から z16 9 枚と 1 段粗くなっていた。
**画面は「それらしく」出るので見て気づけない。** 数字が 1 ずれる箇所:

| 場所 | 基準 |
|---|---|
| `Viewer.getZoom()` / `setZoom()` / `jumpTo({zoom})` | 256 px（= 要求する z） |
| `domain/camera.ts` の `metresPerPixel(lat, zoom)` | 256 px |
| `docs/web_results.md` と `perf/*.mjs` に書いてある zoom 値 | **512 px（MapLibre 時代のまま）**。渡すときに +1 する |

### 操作系

- **ビューキューブ**（右上、`view/viewCube.ts`）。面 6 / 辺 12 / 角 8 の 26 方向を
  クリックで選び、ドラッグで自由回転する。カメラに追従する。
  **依存を増やさないために 2D canvas に 8 頂点を自前で投影して描く。**
  細い回線で効くのは初期チャンクのサイズだけ（`docs/web_results.md`）なので、
  ギズモのために描画ライブラリをもう 1 つ載せるのは筋が悪い。
  カメラの向きを受け取って向きを返すだけなので、メインのレンダラに依存しない
- ズームはホイールとピンチ、向きはキューブ。**+/− ボタンとコンパスは置かない**。
  小さいボタンが 3 つ並ぶより、押せる的が 1 つ大きいほうがよい
- **出典は下辺に常時出す**（`#attrib`）。PLATEAU / 京都府 DEM / 気象庁はいずれも
  表示を求めている。MapLibre の `AttributionControl` が担っていた分で、
  描画層を自前にした以上こちらで持つ
- **鉛直強調**（`[` `]` キーで ×1〜×20 の 5 段）。吉原は 1 km に対して起伏 3 m
  しかないので、強調なしでは横から見ても何も分からない。強調中は PLATEAU 建物を隠す
  （建物は実高のままなので地形と噛み合わなくなる）。
  **メニューに出すのは ×1 / ×5 / ×20 の 3 段だけ。** ×2 と ×10 を押し分ける判断が
  発生しない。判定そのものは強調に影響されない（色は実標高と `h_conn` から決まる）
- カメラプリセット（キーボード 1〜6）。キューブは面のクリックなので、
  俯瞰 52° のような決め打ちの視点は出せない。
  **軸方向のプリセットは正射投影に切り替える**（`O` キーでも切り替わる）。
  透視のままでは「CAD のように断面で見る」にならない。
  **視点はメニューに出さない。** キー 1〜6 とビューキューブが担う。
  `perf/cadshots.mjs` が `top` / `south` / `west` / `iso` を使うので、
  プリセット 6 個そのものは減らさない
- **断面の測線**（`view/sectionTool.ts`）。画面 2 点のクリックを
  `Viewer.unproject` で経緯度に直す。**平面の高さ（`planeZ`）にジオイド高を渡す。**
  既定の 0 は「描かれている地面」ではない（後述）。
  作図中は断面パネルの `pointer-events` を切る。**パネルが画面下半分を覆っていて、
  2 点目がそこに来ると canvas に届かない**（実測で無視されていた）。
  断面パネルは**左メニューの右から右端まで**の帯にしてある（以前は左 292 / 右 176 で
  両側を避けていて、測線が短く描かれ 0〜3 m の起伏がまた読めなくなっていた）ので、
  この処理は必須である。操作パネルは下辺まで伸ばし、断面に高さを譲らない
- **地物のホバー**。カーソルが変わらないと押せることが分からないので、
  `pointermove` で `SemanticsMesh.pick()` を引いて `cursor: pointer` にする。
  **`requestAnimationFrame` で 1 フレーム 1 回に間引く**（毎イベントで raycast すると
  `perf/jank.mjs` が測るフレーム時間に乗る）。ホバー中の id は**ストアに置かない**。
  `store.set` すると購読側の `refresh()`（地形 uniform の更新と断面の再描画まで）が
  毎フレーム走るので、`SemanticsMesh.setHighlight()` が色属性だけ書き換える

### 既定の視点 **[実測]**

注視点は **点群が取れている帯の中心**。AOI の中心（100 ha の真ん中）だと起動直後が
「山と海」になる。見せたいのは吉原の市街で、**そこは点群と PLATEAU 建物が両方ある
唯一の場所**である（点群は歩いた線に沿った 3.17 ha だけ）。

座標は埋め込まない。`catalog.pointcloud.bounds`（EPSG:6674）を `local_frame` の
行列でローカル ENU に直す。**`pointcloud/decode.worker.ts` が点そのものに使っているのと
同じ変換**なので、必ず点群の上に来る。

倍率は `INITIAL_ZOOM = 17.2`。帯（426 × 799 m）が画面幅（17.2 で 843 m）に収まる。
**17.6 まで寄せてはいけない。** `Math.round` で要求する z が 17 → 18 に上がり、
細タイルが 4 倍になって PLATEAU も視界に入る。実測（localhost, 1400×900）:

| z | FMR | time_to_terrain | 要求 | 転送 |
|---|---|---|---|---|
| 16.6（旧既定） | 906 ms | 2,323 ms | 64 | 4.84 MB |
| **17.2（新既定）** | **733 ms** | **1,468 ms** | **64** | **4.84 MB** |
| 17.6 | 1,090 ms | **13,348 ms** | **126** | **6.40 MB** |

要求本数と転送量は旧既定と同じなので、`docs/web_results.md` の枚数・バイト数は
そのまま比較できる。変わるのは時刻だけである。

### パネルの情報設計

以前は `ui/controls.ts` が 8 つの `fieldset` をフラットに並べていた。
**入力（地形条件・水位）と見せ方と道具と出典が同じ階層にあった**ので、
268 px × 56 % の枠では主張の 2 変数を同時に見ることすらできなかった。
分け方は 3 つ。

| 種類 | 例 | 置き場所 |
|---|---|---|
| **変数** | 地形条件、潮位、絞り込み、レイヤ、高さの強調 | 操作パネル。**頭（地形条件と潮位）は固定**し、それ以外だけスクロールする |
| **出力** | 凡例、1 件の内訳、断面図、計測値 | それを出している変数の直下か、専用パネル。**独立した節にしない** |
| **定数** | 参照潮位の値 | 「参照潮位」に畳んで置く。押すと水位が動くので操作でもある |

出典・データの由来・既知の限界の**文章は画面に出さない**。`README.md` と
`docs/results.md` / `docs/data.md` が持っている。**出典表記だけは
ライセンス上の要求**なので画面下辺（`#attrib`）に常時出す。

#### 水位の既定は「普段の海面」

`state.ts` の初期値は `reference_levels_m_tp['MSL']` = **0.314 m T.P.**（気象庁 公表の
平均水面 0.124 m を**測地成果2011 に換算**したもの。天文潮の年平均と一致することで
検算済み。換算は `src/iwagaki/config.py` の `HYOKO_DH_JGD2011_TO_2024 = −0.19031`）。

以前は `catalog.water_level.representative[0]` = **1.0 m** だった。これは
`src/iwagaki/config.py` の `REPRESENTATIVE_H = (1.0, 1.5, 2.0)` から来ていて、
**出典が無い丸い数字**である（`docs/results.md` 自身が「当初は根拠のない代表値として
選んだもの」と書いている）。しかも**既往最高潮位 0.93 m より高い**ので、
起動直後の画面が「記録されたどの潮位でもない水位」になっていた。

水位はすべて**測地成果2011 基準**、地物は信頼可能な 1,217 件が母数
（`docs/results.md`「地物単位の結果」と同じ集計）。

| H | 意味 | 浸水地物 / 1,217 | 判定が変わる |
|---:|---|---:|---:|
| 0.314 | 平均水面（**既定**） | 7 | 7 |
| 0.630 | 朔望平均満潮位（近似） | 50 | 46 |
| 0.690 | 高潮想定の基準潮位 | 67 | 65 |
| 0.930 | 既往最高潮位 | 445 | 106 |
| 1.000 | 旧既定（代表値） | 460 | 155 |

既定ではほぼ 0 件（7 件）になる。**これは意図した状態で**、最初の画面は
「普段はこうです」を示し、そこからスライダを上げて広がりを見せる。
戻れるように頭のチップに `普段` を置いてある。

以前この表は換算前の水位（0.124 / 0.439）と旧い地物数（911）で書いてあった。
**潮位の換算と 3 次メッシュの取りこぼしの修正が両方入っている**
（`docs/results.md`「3 次メッシュの取りこぼし」）。

**`config.py` の代表水位は触らない。** 解析の集計と出力ファイル名
（`changed_H{h}.geojson`）、`docs/results.md` の本文が 1.0 / 1.5 / 2.0 に依っている。
変えたのは viewer の初期値だけである。

守っていること。

- **凡例は節ではなく葉の属性。** 画面に出ている色は 1 セットなのに、以前は
  読む場所が 3 つあった（`Legend` / `PLATEAU 建物の色` / 地形の凡例に混ざった赤）。
  地形の凡例は条件の直下、建物の凡例は「建物の色」の直下に置く
  （用途は 11 種あるので、頭に混ぜると頭が倍の高さになって入力が押し出される）
- **点群の有効範囲は条件から自動で出す**（3.17 ha しか効いていないことを
  隠せる設定にしておく意味が無い）
- **下位オプションは入れ子にする。** 建物の塗り分けは独立した節ではなく
  「PLATEAU 建物」の子
- **チェックボックスが嘘をつかないこと。** 高さの強調中は PLATEAU 建物を隠すので、
  チェック自体を無効にして理由を出す
- **畳む機能は持たない。** 節が 4 つしか無く、畳むと「押さないと分からない」ものが
  増えるだけだった
- **画面のラベルは「潮位」。** 内部の状態名（`waterLevel`）と catalog のキー
  （`water_level`）は変えない。庁内で読むのは潮位で、H は文書側の記号である
- 潮位のスライダには **−/＋** を付ける。ドラッグだけでは 0.05 m 刻みを合わせにくい。
  端で刻みからずれた値（既定の MSL 0.124 など）を**格子に丸め直さない**
  （参照潮位はその値で意味があるので、丸めると出典と合わなくなる）

#### メニューに出す変数と、出さない変数

**状態そのものは削っていない。** `web/perf` の計測ハーネス 28 本が
`setLayer('flood'|'ground'|'semantics'|'pcCoverage')`・`setSurface`（`surfaces.mjs` が
6 値を全部回す）・`setBuildingColor`（`bldgcolor.mjs` が全モード）・`setCamera` /
`setExaggeration` を叩いていて、`docs/web_results.md` の実測値はここから出ている。
**メニューに出さないだけで、`__iwagaki` からは全部触れる。**

| 出さない変数 | 決まり方 |
|---|---|
| `flood`（メッシュの可視） | 既定 true。UI から変えられないが API からは変えられる（`perf/pcshot.mjs` が使う） |
| — | **`waterSurface` と `roads` は出す。** どちらも配信物が増えない（水面は同じタイルを 2 回描くだけ、道路は前から読み込んでいた）ので既定 ON にできる |
| `ground`（乾いたセルを描くか） | 既定 true。OFF は浸水域だけが浮く状態で、用途が無い |
| `semantics` | 既定 true。これが成果物なので消す理由が無い。常時 ON にすると `changedOnly` の依存も切れない |
| `pcCoverage` | **条件が点群系に変わった瞬間だけ**既定値を入れる。`main.ts` の `syncCoverageDefault()` |
| `buildingColor` の `'class'` | メニューは **なし / 用途 / 浸水深** の 3 つ。普通建物／堅ろう建物は浸水の話に効かない |
| — | **`roadColor` は出す。** `一律`（既定）と `通行支障`。既定を通行支障にすると建物の浸水深と色が当たる |

`setLayer('pcCoverage', false)` で切ってから計測しているので、毎回上書きすると
計測条件が勝手に戻る。**UI から変えられない ≠ 値が固定**である。

#### 画面座標 → 世界座標は z=0 で交えてはいけない **[実測]**

**これは絵を見ても気づけない種類。** 地表は `z = geoid(36.955 m) + 標高 * 鉛直強調`
に描かれるので、z=0 平面とレイを交えると地上でずれる。実測（zoom 17.2, 1400×900）:

| 視点 | 画面位置 | z=0 と z=geoid のずれ |
|---|---|---|
| 俯瞰 pitch 52° | 画面上部 (700,300) | 59.8 m |
| 俯瞰 pitch 52° | 画面中央 (700,450) | 47.2 m |
| 俯瞰 pitch 52° | 画面下部 (700,600) | 37.8 m |
| 横から pitch 84°・正射 | 画面中央 | **351.6 m** |

効いていた 2 か所。

1. **地物のピック。** `SemanticsMesh` の塗りメッシュは `position.z = 0` で、高さは
   頂点シェーダが `z = geoid + aGround * uExaggeration` で与えている。
   `Raycaster.intersectObject` は CPU 側のジオメトリしか見ないので z=0 平面と
   交わり、**カーソルより奥（画面では上）の地物が当たっていた**（47 m ≒ 79 px）。
   直し方は「メッシュを撃たない」こと。地物ごとに **その地物が描かれている高さの
   水平面**とレイを交え、ワールド XY で even-odd 内外判定する
   （穴のある footprint も正しく外になる）。AABB で前段を落とすので 1,223 地物でも
   ホバーごとに回せる。**鉛直強調でジオメトリを作り直さない**設計も保てる
2. **断面の測線。** `Viewer.unproject` に `planeZ` を足して、`sectionTool` が
   ジオイド高を渡す。市街の起伏 0〜3 m ぶんの残差（俯瞰で 4 m 弱）は無視する

`Viewer.unproject` の**既定は 0 のままにしてある**。`perf/tileorient.mjs` が
z=0 前提でずれを `parallax()` で自前に補正しているので、既定を変えると二重補正になる。

#### パネルの位置

**ビューキューブの高さを決め打ちにしない。** `ViewCube` には `size: 128` を
渡しているのに host の矩形は **152×158 px** で、インスペクタを `top: 146px` に
置いたら 20 px 重なっていた（実測）。`main.ts` の `placeInspector()` が
キューブの `getBoundingClientRect().bottom` から上端を決める。

操作パネルは下辺まで伸ばし、断面はその右から右端まで。計測パネル（`P`）は
左下が空かなくなったので、操作パネルの右隣の上に置く。

#### 選択とホバーの見せ方

選択は状態としてしか扱っていなかった時期があり、**画面側の出力が 0 個**だった
（クリックすると右上のパネルだけが変わる）。いまは 3 つ出す。

| 出力 | 実体 |
|---|---|
| 選択中の枠線（白・幅 2.4 m） | `SemanticsMesh` の専用 `Mesh`。1 地物ぶんだけ作り直す |
| ホバー中の枠線（水色・幅 1.2 m） | 同上 |
| 周りの減光 | `aColor` を 0.42 倍。**隠しはしない** |

**線ではなく帯（三角形）で描く。** WebGL の `linewidth` はほとんどの実装で 1 px に
固定されるので太い線が引けず、1 px の輪郭では俯瞰で「どれを選んだか」が読めなかった。
幅はメートルで与える（寄れば太く見える）。角は辺ごとの矩形だけでは隙間が開くので、
頂点に正方形を置いて埋める。

**`depthTest: false` で描く。** 地物ポリゴンは地面の高さにあり、
PLATEAU 建物（3D Tiles）の箱がその上に立つので、色属性を書き換えるだけでは
箱に隠れて強調が見えない。

絞り込みと強調が同時にかかるときは**絞り込みが先、強調が後**
（`changedOnly` で残ったものの中で選択を目立たせる）。


#### 画面の色は 1 つの予算である **[実測]**

道路 293 本は前から `objects.geojson` に入っていて描いてもいたが、**建物と
まったく同じ「乾 = 灰 / 浸水 = 青 / 判定変化 = 赤」で塗っていたので、
画面上で道路がどれなのか区別できなかった**（外部からの要望、2026-08）。

ここで **3 回作り直している。** どれも「1 つのレイヤだけを見て色を決めた」
結果で、**色は画面全体で 1 つの予算**だという当たり前を踏み外している。

| 回 | やったこと | 何が起きたか |
|---|---|---|
| 1 | 道路の浸水を **通行支障クラス**（クリーム → 琥珀 → 橙 → 赤）で塗る | 最浅クラスを水色にしていて、水面（水色）の下で消えた |
| 2 | 建物の既定を **浸水深**（灰 / 黄 / 赤）にする | **通行支障の暖色と正面衝突。** 町が一様な黄色の塊になり、道路と建物が区別できなくなった |
| 3 | 道路を **一律のほぼ白**にする | 今度は**非浸水の建物（明るい灰）と明度が近すぎた**。寄ると区別できない |

いまの割り当て。**無彩色は明度で 3 段、有彩色は意味ごとに 1 つ**にしてある。

| | 色 | 何を意味するか |
|---|---|---|
| 地面 | 暗い灰（標高で微変） | 乾いた地表 |
| 建物 非浸水 | **中間の灰** | 浸水しない |
| 道路 | **ほぼ白** ＋ ほぼ黒の縁 | そこが道路である |
| 建物 床下 / 床上 | 黄 / 赤 | 浸水深 0.50 m を境に |
| 水面 | 水色〜紺 / 濃紺 | 浸水深 / 水深不明 |
| 判定が変わる地物 | 朱 | 地形データで判定が割れる |

**道路の既定は「一律」。** 要望は「道路がどこなのか分かるように」であって、
通行支障の色分けは**こちらが勝手に足したもの**だった。建物の浸水深と
色域が重なる以上、両方を同時に既定にはできない。通行支障は
`道路の色` の `<select>` に下げ、**見たい人だけが切り替える**。

**判定が変わったことは輪郭（黄）が担う。** 塗りに 2 つの意味を載せると、
どちらを見ているのかを画面から決められない。
通行支障の閾値は `config.py` の `ROAD_DEPTH_CLASSES = (0.1, 0.3, 0.5)` が
catalog 経由で来るので、ブラウザ側に数字は書かない。

**塗りの不透明度は地物ごとに持てるようにした**（`aAlpha`）。塗りは 0.55 で
建物には足りるが、道路は水面（水深に応じて 0.46〜0.84 の青）の下に入ると
0.55 では消える。道路だけ 1.75 倍して 1.0 で飽和させる。
`vAlpha` は元から頂点シェーダにあって `1.0` を代入するだけの残骸だった。

#### 建物を浸水深（床下・床上）で塗る

外部からの要望は「浸水深 50cm を基準に床下浸水・床上浸水で建物の色を
区別できないか。潮位を上げていくと床上浸水の場所が出てきてしまうことを
表せないか」だった（2026-08）。`buildingColor` に `depth` を足し、
**既定をそれにした。**

最初は `depth` を足しただけで既定は `usage`（用途）のままにしていた。
そのうえドロップダウンに見出しが無く「用途」とだけ書かれた裸の `<select>` だった
ので、**開いた画面のどこにも床下/床上が出ておらず「入っていない」と受け取られた**
（2026-08、再指摘）。選択肢としては存在していたが、要望に対しては届いていない。

直したのは 2 つ。

- **既定を `depth` にする。** このアプリの主題は浸水なので、建物の色も
  既定は浸水深にする。用途は 1 クリック（凡例も用途 11 種より短くなる）
- **`<select>` に「建物の色」の見出しを付ける。** 見出しが無いと、
  中に何が入っているのかが開くまで分からない

既定潮位 0.31 m ではほとんどが「非浸水」になる（吉原 930 棟中 923 棟）。
これは水位の既定と同じ考えで**意図した状態**であり、
スライダを上げると色が入る。

**`depth` だけは属性ではなく水位から決まる。** b3dm の batch table には
`gml_id` が入っているので、地物 assertion の `groundElev` / `hConn` を
**読み込み時に頂点属性へ焼く**（`aGround` / `aHConn` / `aHas`）。
床下 / 床上の判定はフラグメントシェーダが `uWaterLevel` から作る。

- **潮位を動かしても b3dm の作り直しは起きない**（uniform 1 個）。
  水位をここに焼いてしまうとスライダを掴むたびに 22 枚を作り直すことになる
- 地盤高をどの条件から取るかは変わるので、**地形データを替えたときだけ**焼き直す
- **assertion が無い棟（3D Tiles は AOI より広く 2,005 棟を持つ）は
  「非浸水」ではなく「解析範囲外」**として別の色にする。混ぜてはいけない
- **非浸水は中間の灰**（`#9aa1a8`）。明るい灰にしていたら一律の道路（ほぼ白）と
  明度が近すぎて、寄ったときに区別できなかった（上記「画面の色は 1 つの予算である」）
- **凡例の件数は assertion 全件から数える**（読み込めた b3dm タイルではない）。
  3D Tiles は視野の外を取りに行かないので、タイルを数えると
  **625 ha の範囲では数がパンするたびに変わる**。吉原 100 ha は 22 枚が必ず
  全部届くので気づけなかった。「この範囲で床上が何棟」は視野に依らない事実である
- 橋梁・高架など `unreliable` な地物も同じ扱いにする（地盤高が意味を持たない）

閾値 0.50 m の意味は**地盤面からの水深**である。**PLATEAU LOD1 は床高を持たない**
ので、床面を超えたことの証明ではない。凡例に 1 行だけ添えてある。
`docs/results.md`「実際の被害記録との突き合わせ」の 2 点が効く。

- 実測の被害記録は**床上 0 戸 / 床下 39・19 戸**、浸水位 1〜20 cm だった。
  モデルも既往最高潮位 0.93 m で**床上 30 棟 / 床下 277 棟 / 非浸水 387 棟**、
  高潮想定の基準潮位 0.69 m では**床上 0 棟**になる [実測]。
  要望に添えられていた「実際はそこまで潮位が上がる場所は将来的にも少ない」は
  記録ともモデルとも一致する
- ただし**「浸水位」の定義そのものが未確認**で市に照会中（`docs/todo.md` 中 4）。
  地盤面からの水深ではなく床面からの高さなら、閾値の意味が変わる

#### インスペクタは選択中の条件を主にする

4 条件を横並びにすると、地図が 1 条件で塗られているのにパネルだけが 4 条件を
等価に並べる形になり、「いま見ているのはどれか」が読めない。
出すのは `comparisonPair(surface)` の 2 条件だけにする。
**4 条件の表は画面から外した**（畳んでも見ない）。値は `FeatureAssertion` が
持っているので、検算のときは `__iwagaki.store.state.selected` から引く。

- 見出しは `pair.to`（いま見ている条件）
- その下に「`pair.from` との差」（地盤高・浸水深）
- `判定が変わる` / `判定は同じ` のタグも `pair` に対して出す。
  `baseline` を単独で見ているときは比較相手が自分なので `基準そのもの` と出す

#### 小地域ごとの棟数はどう出したか **[実測]**（2026-09-01）

上田氏（舞鶴市）の要望③「浸水建物を国勢調査の小地域（町丁・字等）ごとに集計
できると地域比較ができていい」（2026-08-28）。`scripts/92_area_aggregate.py` が
潮位別の CSV / GeoJSON を書き出す（`docs/results.md`「小地域ごとの浸水建物」）が、
**画面はその焼き込んだ値を出さない。**

**焼かずにクライアント集計にした理由。** `docs/design.md` が
「水位を動かしてもサーバ往復も再計算もしない」を設計の要請にしている。
viewer は既に全建物の assertion（`groundElev` / `hConn` / `unreliable`）を持ち、
`domain/flood.ts::floorCounts` がクライアント側で床上／床下を数えている。
小地域集計はそれを **`area_code` でグループ分けするだけ**（`perAreaFloodCounts`）。
潮位別・モデル別の値を焼くと、水位スライダの各刻み × 2 モデル × 地形条件の
組み合わせぶんテーブルを配信することになり、しかも潮位再生の途中経過は
どのみち焼けない。**建物 1 棟に小地域 ID を 1 個付けておく**のが最小の配信物で、
これは `scripts/83_build_catalog.py` が `scripts/92` と同一の空間結合
（重心 → 小地域ポリゴン、`iwagaki.areas` に共通化）で `objects.geojson` に焼く。
`web/test/area.test.mjs` が両者の一致（総棟数・床上・床下）を全小地域で突き合わせる。

**表を主・コロプレスを従にした理由。** 要望の主眼は**地域比較**なので、
まず「どの町丁が多いか」が一目で分かるランキング表を潮位再生パネルのすぐ下に置く。
浸水棟数の多い順で上位 10 件 ＋「ほか N 地域」＋「(小地域外)」＋「合計」。
合計行は頭の全体棟数（`floorCounts`）と一致する（画面内の検算）。
水位スライダ・潮位再生・モデル切替・地形条件にその場で追従する。

**コロプレスは入れなかった（色予算）。** `#### 画面の色は 1 つの予算である` の
とおり、無彩色は明度 3 段（地面／建物／道路）、有彩色は 黄＝床下 / 赤＝床上 /
青＝水面 / 朱＝判定差 で埋まっている。小地域ポリゴンを塗ると、単色の透明度段階に
留めても既存の地物・水面・道路の上に別の面が重なって「いま何を見ているか」が
読みにくくなる。**地域比較は表で足りている**ので、コロプレスは見送った。
配信側は先に用意してある — `scripts/83` が簡略化した軽量 GeoJSON
（`small_areas.geojson`、属性は `area_code` / `area_name` / `total_bldg` だけ、
潮位別の値は焼かない）を配信し、`catalog.small_areas` に optional で載せる
（`areas.json` / `tide_series` と同じ「無い配信物でも壊れない」パターン）。
コロプレスを足すなら viewer 側だけの追加になる。

## 地形の描き方

`three/terrainTiles.ts` はタイルのピラミッド（可視集合の決定・取得の宣言・
best-available のフォールバック）を持ち、1 枚 1 枚は `three/floodMaterial.ts` の
シェーダで描く。RGBA タイル 1 枚から
**頂点シェーダでテクスチャを読んで格子を変位させる**。

- タイルあたり 128×128 の格子 + 外周スカート。**1 タイル 1 リクエストのまま**
- 陰影は同じテクスチャの隣接テクセルから法線を作って計算する。
  別ピラミッドも追加リクエストも要らない
- 粗メッシュ（z14-15）と細メッシュ（z16-18）はメッシュ同士で z-fight するので、
  細が揃ったら粗を隠す。板なら重ね描きで済んでいた

板（`BitmapLayer`）ではなくメッシュにしたのは、真横・軸方向から見て
「どこが水面より低いか」を確かめるためである。板は横から見れば線でしかない。

### 平常時の水域は下地で塗る **[実測]**

潮位を下げると海と川が「乾いた地面」として描かれ、地形が読めなくなっていた。
原因は 2 つの実測事実の組み合わせである（`data/tiles/highres/17` の 25 枚で計測）。

| 事実 | 値 |
|---|---|
| `h_conn = 0.00` の画素 | **19.26 %**（= 海と川。次の段は 0.25 で、間に値が無い） |
| 標高の最小値 | **0.0 m**（海底は 0 にクリップされている） |
| `A = 0`（到達不能） | 58.2 % |

したがって潮位 0 では `h_conn <= H` は真になるが `depth = H - elev = 0` なので、
浸水色の条件（`depth > 0`）を外れて地面の分岐に落ちていた。

**「濡れているか」ではなく「平常時の海面より低いか」で下地を決める。**
閾値は catalog の MSL（0.124 m T.P.、気象庁 公表・天文潮の年平均と一致で検算済み）。
色は**彩度を落とした鋼色**で、判定の色（鮮やかな水色〜紺の浸水深ランプ、
差分の赤/黄/青）とは別物として読める。差分モードでも同じ規則を先に見る
（見ないと潮位 0 で海が「どちらも浸水」の青になる）。

### 水面は物体として持つ **[実測]**

**以前は「水面」という物体が無かった。** 浸水は地形メッシュの画素を浸水深ランプで
塗るだけだったので、**潮位を動かすと色は変わるが高さは変わらない**。
外部から「可視化していただいている海面は潮位を変えると高さも変動しているのか」と
質問が来て（2026-08）、答えは「していない」だった。

いまは**同じタイル・同じジオメトリ・同じテクスチャを 2 回描く**
（`floodMaterial.ts` の `FLOOD_PASS`）。

| パス | 頂点の z | 何を描くか |
|---|---|---|
| `ground` | `geoid + 標高 * 鉛直強調` | 地面。陰影だけ |
| `water` | `geoid + 潮位 * 鉛直強調` | **水平な水面**。`h_conn <= H` かつ `depth > 0` の画素だけ |

**判定式は 1 行も増えていない。** 水面パスも `h_conn <= H` と `depth = H - 標高` を
そのまま使う（`domain/flood.ts` と同一）。したがって

- **要求するタイルは増えない。** 潮位を動かしてもサーバ往復は発生しない
- **GPU メモリも増えない。** ジオメトリ（`floodGeometry()` の共有 1 枚）と
  テクスチャは 2 枚目のメッシュと共有する

増えるのは draw call と三角形だけである [実測]（1400×900・z17.2・H=1.5）。

| | 水面 OFF | 水面 ON |
|---|---:|---:|
| draw calls | 50 | **75**（= 可視の細タイル 25 枚ぶん） |
| 三角形 | 889,683 | 1,734,483 |
| ジオメトリ数 | 26 | **26** |
| テクスチャ数 | 29 | **29** |

`perf` の不変条件（水位を上げると浸水域が単調に増える / 水位を変えても
リクエストが増えない）は水面 ON / OFF の両方で成り立つことを確認した [実測]。

#### 海が一枚も描かれていなかった **[実測]**（2026-08-24）

水面を入れて配信したあと、外部から**「海面なくね」**と指摘が来た。実際に
**港と湾が背景の黒のまま**で、東舞鶴では画面のおよそ 1/3 が「無い海」だった。

原因は水面パスではなく、**その前からあった** nodata の扱いである。

**航空レーザは水面から反射が返らないので、平常時の水域の大半が 0.5m DEM では
nodata である** [実測]（z17 のタイル全数で計測、AOI 全体に対する割合）。

| | 平常時水域（標高あり） | 平常時水域（**nodata**） |
|---|---:|---:|
| 吉原 | 7.2 % | 12.1 % |
| 西舞鶴 | 1.9 % | **18.0 %** |
| 東舞鶴 | 1.1 % | **31.8 %** |

シェーダは `vValid < 0.999` を **main() の先頭**で捨てていたので、
地形パスも水面パスも nodata を描かなかった。吉原は入江と川の底が 0 m に
クリップされていて「標高あり」で通っていたぶん症状が軽く、
**海の広い範囲を持つ 2 範囲を足して初めて目に見えた**。

**水面を張るのに地面の標高は要らない。** 要るのは 2 つで、

| | どこにあるか |
|---|---|
| そこが水位 H で海と連結しているか | `h_conn`（タイルのアルファ）が持っている |
| 水深 | 標高が無いので **分からない** |

なので `vValid` の discard を**地形パスだけ**に移し、水面パスは nodata でも張る。
ただし **水深を知っているふりはしない** — 深さのランプは掛けず、
「水深不明の開放水面」として一色で塗り、凡例にも 1 行別に出す。

内陸の nodata（建物の影・欠測）はここに来ない。seed に入らないので
`h_conn = ∞` になり、連結の判定で捨てられる（`scripts/30` の `find_open_water`）。

直したあとの画面（既定潮位、操作パネルを除いた領域の画素）:

| | 青い画素 | 背景（描かれていない） |
|---|---|---|
| 吉原 | 10.3 % → **19.0 %** | 36.9 % → 28.1 % |
| 西舞鶴 | 6.8 % → **19.0 %** | 25.1 % → 12.8 % |
| 東舞鶴 | 6.0 % → **25.8 %** | 50.6 % → 30.4 % |

#### 水面を出すときは地形に水の色を塗らない

最初は地形側の浸水深ランプをそのまま残して水面を重ねた。**結果は「水面 ON と OFF の
絵が区別できない」だった** — 地形のランプ（鮮やかな水色〜紺）と水面の色が
ほぼ同じ色で、しかも吉原の起伏は 1 km に対して 0〜3 m しかないので、
水平面と地形面の幾何的な差も画面では出ない。

なので水面 ON のときは**地形を乾いた地面として描き、水は水面メッシュだけが持つ**
（`uWaterSurface`）。差分モード（赤/黄/青）は地面の主張なのでそのまま残す。

水面の色は 2 つの決めごとを持つ。

- **ランプは 0〜2 m で振る。** 0〜3 m だと市街の浸水深がほぼ最浅端に固まり、
  一様な水色になる（市街部の標高が 0.5〜3 m しかないため）
- **汀線（浸水深 10 cm 以内）を白く出す。** 潮位を動かしたときに動くのは
  面の色ではなく水際の位置なので、そこが読めないと「高さが変わった」が伝わらない

### 窪地は「浸水しない」と同じ色で潰さない **[実測]**（2026-08-25）

外部から**「東舞鶴は 0.8 m の潮位でも浸水する範囲があるはずなのに着色されない」**
「**地盤高が 0.8 m のところで潮位を 0.9 m にしても浸水深が 0 のまま**」と指摘が来た。

調べた結論は**コードの誤りではなく、連結性モデルがそのとおりに効いている**である。
東舞鶴の市街は**海側の護岸天端 1.0〜1.3 m に囲まれた 0.8〜1.0 m の窪地**だった
（0.5m DEM の断面、港の水面 → 市街、単位 m）。

```
2.4 2.3 2.2 2.3 2.7 1.9 | 0.2 ×9 | 1.0 1.1 1.3 1.1 0.8 0.9 1.0 0.9 1.0 ...
      埠頭側              港の水面    護岸天端 1.0〜1.3     市街の中は 0.8〜1.0
```

その結果 `h_conn` の分布が**潮位 0.5〜0.95 m の帯でほとんど止まる** [実測]。

| `h_conn` の帯 | ≤ 0.45 | **0.50〜0.95** | 1.00〜1.25 |
|---|---:|---:|---:|
| 市街（旧 625 ha の範囲・陸 385 ha） | 9.02 ha | **1.37 ha** | 14.23 ha |
| 東舞鶴 全体（1,000 ha・陸 760 ha） | 11.51 ha | **4.24 ha** | 29.18 ha |

**潮位を 0.45 → 0.95 m と 0.5 m ぶん上げても市街では 1.4 ha しか増えないのに、
次の 0.3 m（1.00 → 1.25）で 14.2 ha 増える。** 天端を越えて初めて中に入るためで、
市街の主要部は 1.25 m でまとめて浸かる。

丸めのせいではない [実測]。標高を一律 0.05 m 下げて `h_conn` を計算し直しても、
潮位 0.90 m の浸水域は **15.75 ha のまま 0.0000 ha も変わらない**
（東舞鶴は 0.1 m 刻みの DEM。`docs/data.md`「鉛直の刻みは図郭によって違う」）。

モデルとしては正しいが、`docs/design.md`「既知の限界」2 のとおり
**排水路の吐口にフラップゲートが無い**（市への照会、2026-08）以上、
地表面の連結性しか見ない本モデルは**内陸側を過小評価している**。
だから「浸水しない」と同じ灰で潰さず、**窪地**として別に出す。

| 状態 | 条件 | 出し方 |
|---|---|---|
| 浸水 | `h_conn <= H` かつ `depth > 0` | 浸水深ランプ（水色〜紺）／水面メッシュ |
| **窪地** | `h_conn > H` かつ **標高 < H** | **画面座標の斜線**（彩度を落とした水色） |
| 非浸水 | 上のどちらでもない | 地面 |

3 状態は**排他かつ網羅**である（標高 = 潮位ちょうどは水深 0 なのでどれでもない）。
`test/parity.test.mjs` がフィクスチャの全地物 × 全水位で確認している。

決めごとが 3 つある。

- **配信物は 1 バイトも増えない。** 標高（RGB）と `h_conn`（A）は
  もともと**同じ画素**に入っているので、両方を引けばその場で判定できる
  （`RGBA タイルのパッキング`）。タイルも再計算もサーバ往復も発生しない
- **面の色ではなく斜線にする。** 浸水と窪地は**根拠が違う**（海から連結して
  到達する / 標高が潮位より低いだけ）ので、同じ強さで塗らない。
  斜線は `gl_FragCoord` で振る = 画面座標なので、ズームしても縞の太さが
  変わらず「地形の属性」ではなく「こちらが重ねた印」として読める
- **新しい色相は足さない。** 画面の色は 1 つの予算で、地面＝暗い灰 /
  建物＝灰・黄・赤 / 水＝青 / 道路＝ほぼ白 で埋まっている。
  窪地は**水の色相を薄めて借りる**（`#70bfcc`）

地物側も同じ判定を持つ。

- PLATEAU 建物の `浸水深（床下・床上）` に **`窪地`** の区分が増える
  （uniform 1 個。b3dm は作り直さない）。東舞鶴 6,308 棟のうち
  潮位 0.80 m で **34 棟**、0.90 m で **90 棟**、既往最高潮位 0.93 m で
  **201 棟** [実測]
- 地物パネルは**「浸水深 0.00 m」で終わらせない。** 窪地なら
  `潮位より低い 0.10 m` の行と、「地表面をたどると海に出ないので 0 になる
  （海側からつながるのは 1.25 m から）」「吐口にフラップゲートが無いので
  実際には管路を逆流して浸水しうる」を出す。**指摘そのものへの答えを
  パネルが持っていなかった**のが元の問題である

差分モードでは出さない。2 条件の `h_conn` を比べる画面で
**どちらの条件の窪地なのかを色 1 つで表せない**ため。

**この節は続きがある。** 上の結論（窪地を別の印で出す）は、**次の節で既定から
外れた**。市の回答が「単純に 潮位 − 地盤高 でよい」だったためで、窪地という区分は
`海からつながる` を選んだときにだけ現れるものになった。

### 窪地を別に出すのでは足りなかった — 既定を「潮位 − 地盤高」にする（2026-08-26）

前節の窪地表示を見せたところ、市からの回答は

> ご指摘の通り、精度高いシミュレーションをするためには上記のデータが必要になります。
> が、現状整理できていないというのが課題です。
> **現場にいる経験則として、市内全域的に、排水路などを通じて、潮位よりも地盤高が
> 低い箇所は、その差だけ浸水している状況です。**
> 現時点では、単純に「潮位ー地盤高＝浸水深」として可視化することで問題ないと思いました。

だった。**窪地は「浸水しうる土地」ではなく、現に浸水している土地だった。**
斜線という 1 段弱い印は、そこを「留保つきの浸水」として出していたことになる。

なので浸水の決め方そのものを状態にする（`domain/types.ts` の `FloodModel`）。

| モデル | 浸水 | 浸水深 | 既定 |
|---|---|---|---|
| **単純** | `標高 < 潮位` | `潮位 − 標高` | **○** |
| 連結 | `h_conn ≤ 潮位` | 同上（連結しなければ 0） | |

- **単純 = 連結 ∪ 窪地** である。切り替えで浸水域が減ることは無い。
  `test/parity.test.mjs` がフィクスチャの全地物 × 全水位で押さえている
- **配信物は 1 バイトも変わらない。** 単純モデルはタイルの RGB（標高）だけを見る。
  `h_conn`（A）は焼いたまま残り、切り替えは uniform 1 個（`uSimple`）で済む。
  PLATEAU 建物も同じ（地盤高と `h_conn` は頂点属性にあるので b3dm は作り直さない）
- 単純モデルでは窪地という状態が消えるので、**`重ねる` からチェックごと外す**。
  押しても何も変わらない項目を残さない
- **`判定差` だけは 2 条件の地盤高が要る。** 到達する側の地盤高は地形タイルの RGB に
  あるが、出発する側はどこにも無かった。差分タイルの **B は 0 で空いていた**ので、
  そこに出発する側の地盤高を `h_conn` と同じ刻みで詰める（`scripts/80` の `elev_code`。
  1..255 = 0.00..12.70 m で、水位スライダの上限 3.00 m を覆う）。
  **B が 0 の画素は焼き直す前の配信物**なので、そこだけ連結モデルに落ちる
  （落とさないと古いタイルで全画素が「浸水しない」になる）。
  **タイルを焼き直すまで `判定差` は連結モデルのまま出る。**
- **画面から「何を計算しているか」が読めること。** 凡例の色では決め方は分からないので、
  見出し行（`nowline`）に `潮位 − 地盤高` / `海から連結` を常に出す

**連結モデルは消さない。** 排水路の吐口高・フラップゲートの有無が手に入ったら、
精緻化するのは連結モデル側（`h_conn` の seed に吐口を足す）である。
単純モデルはその間の暫定であって、上位互換ではない。

### 浸水深より先に地盤高を見せる（2026-08-26）

同じ回答に続きがある。

> そういう意味では、浸水深を見せる前に、どの場所の地盤が低いのか、
> 地盤高を色のグラデーションで見せていくのもありかと思いました。

`地形の色` に **`地盤高`** を足す（`domain/types.ts` の `TerrainPaint`）。
**配信物は増えない** — 標高はもともとタイルの RGB にある。

決めごとが 4 つ。

- **振れ幅は 0〜3 m。** 水位スライダの帯と揃える。AOI の実レンジ（0〜285 m）で
  振ると、市街の 0.5〜3 m がランプの最下端に固まって一様な色になる。
  3 m を超えると地面の灰へ抜ける
- **色相は紫。** 画面の色は 1 つの予算で、地面＝灰 / 建物＝灰・黄・赤 / 水＝青 /
  道路＝ほぼ白 / 判定差＝赤・黄 が埋まっている。**空いているのは紫だけ**である。
  単色ランプなので、色覚の型に依らず低い順に読める
- **低い側を暗くしない。** 0 m を黒紫に置いたら、暗い画面の地の色や nodata の穴と
  見分けがつかず、**いちばん見せたい土地がいちばん沈んだ**。明度ではなく
  **彩度**で高さを送る（低い＝鮮やか、高い＝灰へ抜ける）
- **面には浸水の色を一切出さない。** 浸水域・窪地・判定差をここに重ねると、
  結局どちらを読む絵なのか決まらない。潮位との関係は
  **いまの潮位の等高線 1 本**（白）だけが担う。水面メッシュも潮位ではなく
  **平常時の海面**に置く。潮位まで張ると、いちばん見せたい低地が青で隠れる。
  かといって水面を消すと、航空レーザが値を返さない港と湾が穴になる

**`地形の色` は頭（固定部）に置く。** スクロールの下に埋めると開いた画面から
見つからない。建物の色で一度それが起きている（`state.ts` の `buildingColor`）。

### 仮定の深さを面に出す — 「仮定の段階」（2026-08-27）

仮想排水路（S2）を足したあと、画面には「排水モデルの差」（S1 と S2 の判定差）が
あったが、**その差がこちらの仮定に依存していることは絵から読めなかった**。
市に出した方針（2026-08-26）に

> 色分けで「確実に浸水しそうな場所」と「データ不足で判断が難しい場所」を分けて表示

と書いた分がここに当たる。

**当初の設計（`docs/flood_simulation_spec.md` §8）は使えなかった。**
不確実性の軸を吐口の敷高（±0.20 m）に置いていたが、**3 ケースで結果がほぼ
完全に一致する**（`scripts/32` を越流点ベースにする前は既往最高潮位で 24.85 ha が
3 ケースとも同じ、差は 9〜11 セル。越流点ベース後も東舞鶴 +0.20 m で 20.46 →
20.18 ha の 0.28 ha 差にとどまる）[実測]。吐口ペアが潮位 0.93 m でほぼ全部
seed になり、どこまで広がるかを決めるのは敷高ではなく DEM だからである。

軸を**モデルの入れ子**に替えた。

```text
S1（海から地表で連結） ⊆ S2（仮想排水路を逆流） ⊆ 潮位以下（地盤高 ≤ H）
```

| 段 | 浸かると言うのに要る仮定 | 出し方 |
|---|---|---|
| **3** | 無し。海から地表面をたどって届く | **面の色**（判定差の「どちらも浸水」と同じ青） |
| **2** | 吐口があるという仮定が要る | 斜線 |
| **1** | 潮位以下なだけで到達経路を示せない | 弱い斜線 |

決めごとは 4 つ。

- **配信物は 1 バイトも増えない。** 3 段はすべて既存の `diff_drainage` タイルに
  入っている（R = `h_conn(0.5m)`、G = `h_conn(S2)`、B = 地盤高）。
  **単純モデルでは「浸水し始める水位」がそのまま地盤高**なので、B は h_conn と
  同じ符号化・同じ比較で 3 段目になる。新しいピラミッドは焼かない
- **仮定が要るものを面の色で塗らない。** 窪地の印と同じ理由づけで、下の 2 段は
  `gl_FragCoord` の斜線にする。画面座標なのでズームしても縞の太さが変わらず、
  「地形の属性」ではなく「こちらが重ねた印」として読める
- **新しい色相は足さない。** 浸水の青を薄める方向だけを使う
  （`#295794` → `#4d8fc2` → `#8cbddb`）。塗りの強さがそのまま仮定の深さになる
- **水面は潮位ではなく平常時の海面に置く。** 地盤高モードと同じ理由で、
  潮位まで張るといちばん見せたい「仮定が要る土地」が青に隠れる

**確率とは呼ばない。** 段はモデルの入れ子であって重みも分母も無いので、
段数を割った比率は出さない。凡例にもその 1 行を出す。

**仮想排水路が絵に効いている画面には注意書きを常時出す**（仕様 §1 の必須表示）。
吐口の位置・敷高・逆流防止施設の有無は市も把握できておらず、こちらが置いた仮定である。

**GLSL のコンパイルエラーは実行時にしか出ない**ので、typecheck と build では
足りない。`web/perf/assumshot.mjs` が 3 モードを順に描いて、3 段が画面に
出ていることと console エラーが無いことを見る。判定そのものは配信済みタイル
1,154 枚（東舞鶴 693 / 西舞鶴 461）を復号して解析ラスタと突き合わせた
（`docs/results.md`）。範囲は `AREA=nishi_maizuru` で選ぶ。

### 水みちと窪地をどう出したか（2026-09-01）

外部プロダクト FARR（mite-shiru 社）のロジック取り込み（`docs/todo.md`「FARR の
ロジックを取り込む」）。**iwagaki が明示的に「やらない」内水・地表流の集中**を
別オーバーレイとして足した。**潮位判定（`h_conn`）には一切混ぜない。**

- **水みちは「地形の色」の 3 つ目**（`flood` / `elevation` の隣。`domain/types.ts` の
  `TerrainPaint`）。`elevation` と同じく**潮位を使わない面**で、浸水の色は出さない。
  一様降雨で地表流がどこに集まるか（flow accumulation）を log スケールで塗る。
  凡例に **「一様降雨・地形のみ。浸透・管路・実際の降雨分布は含まない」**を常時出す。
- **越流点マーカーは「重ねる」の別レイヤ**（`窪地の越流点`）。DEM だけで決まる
  海に通じない窪地と、その鞍部（越流点）を ▽ で置く。面積上位のみ（highres で
  窪地は 6,000 超あるので全部は置けない。`scripts/33` が上位 60 件に絞る）。
- **既存の「窪地（逆流で浸水しうる）」斜線とは別物。** あちらは
  `標高 < 潮位 かつ h_conn > 潮位` の**潮位依存**（`floodMaterial.ts` の `pondedFill`）で、
  こちらは潮位を知らない**原理版**（Priority-Flood の充填深・越流点標高）。
  同時に ON にできる。凡例でも「潮位非依存」と明記して混同を防ぐ。

**色の予算。** 画面の色は 1 つの予算（地面＝灰 / 建物＝灰・黄・赤 / 水＝青 /
道路＝ほぼ白 / 窪地＝薄い水色）。水みちは**新しい色相を足さず**、水の青を
借りて 地面 → 水色 → 紺 → 紺黒 のランプにした（`docs/images/flow_accum.png` の
`cubehelix_r` に寄せる）。窪地セル（充填深 > 0）は同じ薄い水色（`#70bfcc`）へ寄せ、
越流点マーカーもその水色にする。**形（面の濃さ／▽ マーカー）で区別**し、色相は増やさない。

**タイルのパッキング**（`scripts/80_build_web_tiles.py`、条件ごとに 1 ピラミッド）:

    R  水みち = round( log(1+集水セル数) / log(1+accum_max) * 255 )
       8bit で足りる（色ランプ 1 本ぶん）。16bit（R=hi, G=lo）にすると R,G が
       高エントロピなノイズ場になり PNG がほぼ 2 倍に膨らんだ [実測: z18 highres
       で 4.1 → 7.5 MB]
    G  予備（0）
    B  充填深コード（h_conn と同じ 0.05 m 刻み。0 = 窪地でない）
    A  0 = データ無し、255 = あり

`accum_max` はタイルに入らないので `catalog.flow.<条件>.accum_max_cells` に載せる。
**吉原（100 ha）は z17・面的表示用の 2 範囲（625/1000 ha）は z16 まで**
（水みちは定性的なオーバーレイ。z18 まで焼くと 8bit log のノイズ場が支配して
highres で 4 MB、z17 だと広い範囲で 8〜12 MB になった [実測]。俯瞰で見る範囲なので
1 段の解像度より枚数を優先）。`drainage` 条件は `highres` と同じ地形なので焼かない
（`domain/flow.ts` が `highres` にフォールバック）。

**越流点は `three/pourPoints.ts`。** 線路（`railwayLine.ts`）と同じ立て付け:
ワールド座標の板・標高は GeoJSON の第 3 座標（越流点標高）に焼き込み・prefetch で
何も待たせない・`Group` の `renderOrder` は 46（線路 45 の上）。充填深で 3 段の大きさ。

### クリックで集水域を抽出する（2026-09-01・FARR 取り込みの最終段）

**水みちモードで地図をクリックすると、その地点の上流（集水域）を面で出す。**
インスペクタに**ハイライトした面の面積**と流出先を出す。FARR の「クリックで
集水域抽出」にあたる（`docs/todo.md`「FARR のロジックを取り込む」）。

**配信は事前分割した流域ポリゴン**（案 B）。receiver グリッド（D-inf は
`receiver1/receiver2/prop1/prop2` の 4 枚）を 0.5m 全域でクライアントへ送るのは
非現実的で、サーバ往復は「水位を動かしてもサーバ往復しない」（本ファイル冒頭）と
相反するので却下。代わりに解析側（`src/iwagaki/flow.py` の `flow_basins`、
`scripts/33`）で

- 主 receiver（D-inf の配分の大きい方）の**流下木**を作り、
- 本流セル（`accum >= FLOW_BASIN_CHANNEL_MIN_AREA_M2`）の**合流点で切って**
  数十〜数百個のリーフ部分流域にし（小さいものは隣へ併合、上限
  `FLOW_BASIN_MAX_COUNT`）、
- 各リーフに**下流のリーフ id**（`downstream_basin_id`、AOI 内の終端は −1）を持たせて
  簡略化ポリゴンで配信する（`catalog.flow.basins`。highres 1 本、吉原で ~170 個・
  168 kB）。

viewer は `domain/flow.ts` の純関数（three/deck を import しない）:
`basinAt`（クリック点を含むリーフを奇遇則で探す）→ `catchmentOf`（`downstream` を
逆にたどってリーフ＋上流の全リーフを集める）→ `catchmentSummary`（面積の合計・
端で切れているか・流出先）。ハイライトは `three/catchmentLayer.ts`（`ShapeGeometry`
の薄い面＋縁取り、深度テストを切って地形の上に出す、`renderOrder` 47）。

**インスペクタに出すのは面の面積だけ。** 吐口の D-infinity 集水（geojson の
`max_accum_*`）は主 receiver で切った流域境界を分流が跨いで出入りするので面積と
一致せず、数字で並べると紛らわしい。解析からは geojson で参照できる。

**クリック点の経緯度は `viewer.unproject` を標高 0（ジオイド面）で交える**
（`sectionTool` と同じ規約）。地表は `geoid + 標高 * 鉛直強調` に描かれるので、
**鉛直強調 > 1 かつ俯角の付いた視点では山側で数十 m ずれ、隣の流域を拾いうる**。
水みちは俯瞰で見るオーバーレイで、既定の鉛直強調 ×1 では真下に交わるため誤差 0。
地形を実際に raycast する厳密版は別 PR（`sectionTool` も同じ課題を「残差は無視」で
受けている）。

**collar と clip。** ルーティングは AOI 外周に GSI 5m の collar を張って解き
（`route_with_collar(..., want_basins=True)`）、流域を **AOI 矩形に clip** する。
集水域が collar 側／AOI 外へ延びる流域は `edge_truncated` を立て、インスペクタで
「集水域が表示範囲の外へ延びている。実際の集水域はこれより広い」と断る（出す面積は
AOI 内に入っているぶんだけ）。

**色は増やさない。** 集水域の面は水みちの青緑の上に**明るいクリーム白の洗い**
（α 0.30）＋濃い縁。新しい色相は足さず明度で「選択されている」を出す（越流点▽・
線路と同じ方針）。**水みちモードを外すと選択もハイライトも消える**（`main.ts`）。

**断面ツールとの接続（流域の主流路に沿って自動で測線を引く）は入れた**
（2026-09-01、別 PR）。`main_channel_from_outlet`（`src/iwagaki/flow.py`）が D-inf の
主 receiver 木を合流点で切って主流路のポリラインにし、`scripts/33` が
`flow_channels_<条件>.geojson`、`scripts/83` が `catalog.flow.channels` として配信する。
viewer は流域を選んだ状態で断面パネルが**既に開いていれば**主流路の頂点を区間ごとに
`sampleLine` で辿って距離を積み上げる（`main.ts` の `buildSectionAlongChannel`）。
**パネルを新たに開きはしない** — 集水域の選択は面積・最大集水を見るのが主目的で、
毎回パネルが画面下半分を覆うのは押し付けが強い。手動の 2 点断面（`sectionTool`）は
このパスを経由せず、そのまま動く。

### 地点＋徒歩圏のクリックを既存のツールと取り合わせない（2026-09-02・複数自治体からの要望 T1）

T1（`docs/todo.md`）の「地図を 1 点クリックして中心を指定する」（`view/pointPickTool.ts`）
は、上のクリック集水域抽出・断面ツール（`sectionTool`）と**同じ canvas の click/pointer

どれか 1 つだけが有効になるよう `main.ts` に規約を置いた。

- **`sectionTool` と `pointPickTool` は互いに排他。** 片方を開始する前に、もう片方が

- **hover（ホバー中のカーソル変更）も `pointPickTool.isActive` を見る。** 見ないと、

### 線路が見えなかったのは色ではなく描画順だった **[実測]**（2026-08-25）

市が「表示範囲の東側を**赤破線で示す JR 線路まで**」と地図で指してきたので
範囲を広げたが、**その基準線そのものが画面に無かった**。
「どこまで広げたのか」が絵から読めないので線路を足す。

**PLATEAU 舞鶴市に鉄道は入っていない**（`docs/data.md`「鉄道は入っていない」）ので、
これだけ国土数値情報 (N02) 由来である（`scripts/12_fetch_railway.py`）。

**見え方で 3 回やり直した。** 記録しておく価値があるのは、
**3 回のうち 2 回は原因を取り違えていた**からである。

| # | やったこと | 結果 |
|---|---|---|
| 1 | `LineSegments`（1 px・黒白の交互） | **読めない。** WebGL の線幅は 1 px 固定 |
| 2 | ワールド 9 m のリボン | **まだ読めない。** 4 km 幅の画面で 2.4 px |
| 3 | 頂点シェーダで画面座標の最小太さ | **さらに悪化。** 1.3 km の線が画面に 80 px しか出ない |
| 4 | **Group に入れて Group の `renderOrder` を 45 に** | **読めた。** マゼンタ画素 104 → **2,301** [実測] |
| 5 | 色を**黒白の鉄道記号**に戻す | 「ピンクは微妙」と再指摘。**原因が色でなかった以上、色相を消費しない方が良い** |
| 6 | **細く・弱く・道路と同じ深度**に | 「浮いている」「紙の地図や Google マップはこんなにはっきりさせない」と再指摘。**見えなかった時期の埋め合わせで太く強くしすぎていた** |

**本当の原因は色でも太さでもなく描画順だった。** 下の
「`Group` の `renderOrder` は子より先に比較される」と同じ罠で、
Mesh 側に `renderOrder = 40` を置いていたが、
**地物の Group が 30 を持っているので地物が後に描かれ、道路と建物に
上塗りされていた**。線が見えていたのは建物の隙間だけだった。

同じ画面で測った数字（1400×900・潮位 0.93 m・マゼンタの画素数、操作パネルを除く）:

| | 起動時の広域 | 寄ったとき（z16.4） |
|---|---:|---:|
| Mesh に renderOrder 40（誤り） | 104 px | 183 px |
| **Group に renderOrder 45** | **2,301 px** | **5,175 px** |

**色を変えても太さを変えても 100 px 前後から動かなかった**のに、
描画順を直した瞬間に 20〜50 倍になった。**絵が薄いときは、まず塗り重ね順を疑う。**

決めごとは 4 つ。

| 決めごと | なぜ |
|---|---|
| Group の `renderOrder` を 45 | 地物の Group が 30。**Group の値が先に効く**ので Mesh 側では足りない |
| 幅はワールドの 7 m | **複線の路盤の実寸。太くしない。** 一度 16 m まで広げたが、それは見えなかった原因を太さだと誤診していた期間の名残で、直った後は「浮いている」と読まれた |
| **`depthTest` は道路と同じく入れる** | 切って最前面に出すと地形と建物の上を素通しで走り、**地図に載っているのではなく上に貼ってあるように見える**。`semanticsMesh` の `material()` と同じ `depthTest: true` / `depthWrite: false` にし、z を +0.12 m 持ち上げて z-fight を避ける（道路の輪郭が +0.10 m） |
| 色は**濃灰の縁 ＋ 濃灰/生成りの刻み**（周期 11 m） | 地形図・Google マップ・PLATEAU と同じ鉄道記号。**色相を 1 つも使わない**のが利点で、画面の色の予算（地面＝灰 / 建物＝灰・黄・赤 / 水＝青 / 道路＝ほぼ白 / 窪地＝薄い水色）に手を付けずに済む。**純黒・純白にはしない** — 線路は主題（浸水）ではなく基準線なので、探せば読めるが目を引かない濃さに置く。不透明度 0.92 は「引いたときに点が消えない」下限として決めた |
| **縁を濃灰で締める**（半幅の外 24 %） | これが要点。縁が無いと明るい刻みが**一律ほぼ白の道路と融ける**。最初の失敗（`LineSegments` の黒白 1 px）はまさにこれだった |
| 標高は**頂点に焼いてある** | `scripts/12` が 0.5m DEM から引く。地形タイルを待たずに描け、鉛直強調は uniform 1 個で済む |

刻みはフラグメントで作る（累積距離を varying で渡す）。頂点属性で持つと
頂点間で補間されて縞の境目がぼける。

**5 回のうち 4 回、直したのは間違ったつまみだった。** 色 → 太さ → シェーダの
細工 と回して効かず、効いたのは描画順（見えるようにする側）と
`depthTest`・太さ・濃さ（弱くする側）だった。**絵が思ったように出ないとき、
最初に疑うべきは色ではなく、いつ・どの深度で塗られているかである。**

線路が掛からない範囲（吉原 100 ha）では `重ねる` にも凡例にも出さない
（`layersOf()`。点群と同じ規則）。出典も出す範囲にだけ足す。

### `Group` の `renderOrder` は子より先に比較される **[実測]**

**2026-08-25 にもう 1 回踏んだ。** 線路レイヤを Mesh の `renderOrder = 40` で
足したら道路と建物に上塗りされた（上の節）。**同じ罠なので、
地形の上に何かを重ねるときは必ず Group ごと順番を持たせること。**

**これも絵を見ても原因に辿りつけない種類だった。** 水面を張った瞬間、
浸水域の道路と建物のポリゴンが**完全に消えた**。色の問題に見えるが違う。

three の `projectObject` は `object.isGroup` なら `groupOrder = object.renderOrder`
として子に配り、`sort` は **`groupOrder` → `renderOrder`** の順で見る。
`TerrainTiles` は Group の `renderOrder` を 0（粗）/ 1（細）にしてあるのに、
`SemanticsMesh` の Group は 0 のままだった。したがって

```
groupOrder 0: 粗タイル(0) → 粗の水面(5) → 地物の塗り(10) → 地物の輪郭(11)
groupOrder 1: 細タイル(1) → 細の水面(6)          ← 地物より後に描かれていた
```

**細タイルとその水面が地物より後に描かれていた。** 地物の塗りは
`depthWrite: false` なので深度を残さず、後から来た地形（不透明度 0.95）と
水面（0.46〜0.84）に上書きされる。**水面を入れる前から地物は洗われていた**
（道路が輪郭線しか見えなかったのはこれ）。水面が来て初めて症状が見えた。

`SemanticsMesh` の Group に `renderOrder = 30` を与えて直した。
PLATEAU 建物は不透明なので不透明リスト側で先に描かれ、深度も書くので、
地物の塗り（地盤面）は建物の下に隠れたままである（順序を上げても屋根を突き抜けない）。

### タイルの読み方で守ること

3 つとも**絵を見ても間違いに気づけない**種類なので、明示しておく。

| | 内容 |
|---|---|
| **area-registered** | タイルは 1 画素 = 1 セルで焼いてある（`scripts/80` が `from_bounds(..., 256, 256)`）。セル k は uv `[k/256, (k+1)/256)` を占め、**中心は `(k+0.5)/256`**。point-registered として引くと半セルずれ、ずれ量がズームで変わるので、複数ズームが同時に描かれる俯瞰視で段差になる |
| **南北の向き** | タイルは 1 行目が北。テクスチャの `t=0` が北辺になる一方、格子の uv は **`v=0` が南**。引く前に `1-v` する。法線の y 成分も同じ向きに揃える（面 `z = f(x,y)` の法線は `(-fx, -fy, 1)`）。**画面と焼いたタイルを直接照合しないと捕まらない**ので `perf/tileorient.mjs` で見る |
| **nodata を補間しない** | 標高は 4 点の双線形で読むが、1 点でも nodata（`R=G=B=0`）が混ざったら最寄りに落とす。混ぜると −9999 から実標高へのランプができ、海際に平らな棚が生える。`h_conn` は判定値なので**常に最寄り**で引く |

## 点群の実行時

### 4 つに割る

```
COPC (R2) ──Range──▶ CopcIndex ──▶ LodSelector ──▶ Scheduler ──▶ DecodePool ──▶ Renderer
                     octree        純関数         優先度        Worker+WASM    差し替え対象
```

この割り方が成立するのは copc.js の形のおかげである **[実測]**。

- `Getter = (begin, end) => Promise<Uint8Array>` を差し込めるので、
  **COPC の IO を全部 scheduler に通せる。** copc.js が勝手に fetch することはない
- `Hierarchy.Node` が `pointDataOffset` / `pointDataLength` を持つので、
  どのノードがファイルのどこにあるか事前に分かる。range coalescing を自前で書ける
- decode は「取得済みバイトを返すだけの getter」を Worker 内で渡す。
  **取得とデコードが完全に分かれる**

### hierarchy は 1 リクエストで取る

COPC の octree 索引は「1 ページ読む → 子ページの位置が分かる → また読む」という
**依存チェーン**で、素朴に辿ると往復回数がそのまま待ち時間になる。

仕様上、全ページは `user_id='copc'` / `record_id=1000` の EVLR 1 個に連続して入っている。
そこを 1 リクエストで取り、以後はメモリから切り出す（`pointcloud/copcIndex.ts`）。
EVLR が見つからない場合や大きすぎる場合はページ単位取得に戻す。

### LOD

深さ `d` のノードの点間隔は `spacing / 2^d`。それが画面で何 px になるか
（screen-space error）で採否を決める。

```
sse(node) = (spacing / 2^depth) * (viewportHeight / 2) / (distance * tan(fovY / 2))
```

- 閾値を下回るノードは落とす。加えて**地面に落とした視錐台（台形）**で絞る。
  外接矩形では傾けた視野でほぼ 2 倍の面積を残してしまう（`perf/frustum.mjs`）。
  判定は分離軸で、余白はノード側の箱を広げて取る（`domain/camera.ts`）
- `maxPoints` / `maxBytes` に収まるまで、粗い順・画面で大きい順に採る
- `maxBytes = clamp(帯域推定 * 2, 1 MB, 20 MB)`。
  **係数 2 = 「点群に使ってよいのは 12 秒の窓のうち 2 秒ぶん」**で、
  残りは地形・建物・地物に要る（`docs/web_results.md`）

### 色は点群自身の RGB を使う **[実測]**

配信している COPC は **PDRF 7 / 36 バイト**で、`Red` / `Green` / `Blue` を
**実データとして持っている**（先頭ノード 12,174 点で min 2〜255・mean 126〜140・
40 種類以上）。バックパック SLAM（LiBackpack）はカメラ付きで、
0.08 m ボクセルの間引きと COPC 化を通っても色が残っていた。
`Classification` は全 0（未分類）、`ReturnNumber` は全 1 なので地面/非地面の分類は無い。

**バイト列は既に取得・展開してあるので、RGB を読むのに追加の通信は 0 バイト。**
増えるのは decode worker の getter 3 本ぶんの CPU だけである
（`docs/web_results.md` の decode 実測値はこの変更より前のものなので、
決め手にするなら測り直すこと [未確認]）。

標高ランプで塗り直すのをやめた理由は 3 つ。

| | 内容 |
|---|---|
| 絶対標高は点群の役に立たない | 市街は **T.P. 0〜3 m しか無い**ので、どんなランプでも肝心の帯が潰れる。地面と 3 m 先の壁が別色になるだけで、読みたいものが出ない |
| どの色相を選んでも主張と衝突する | **青は浸水深、赤と黄は判定差、黄は点群の被覆線、緑は断面の系列**が使っている。虹はそのすべてと重なり、単一色相にしても残りと当たる |
| 実測色なら説明が要らない | 「これは現況の観測、青いのは我々の判定」が色だけで分かる（`README.md`「役割を分けて突き合わせる」） |

**彩度も明るさも触らない。** 一度 1.15 倍に起こしていたが落とした。
実測色を作り変えないためで、見た目もほとんど変わらない
（1.35 まで上げると SLAM のノイズ点＝空に散る水色が目立つ、という副作用だけがあった）。
RGB を持たない配信物（DTM から作った合成点群）に当たったときだけ
紫の単一色相ランプに落ちる。

### バイト予算に「もう持っているノード」を数えてはいけない **[実測]**

`maxBytes`（= 帯域推定 × 2、上限 20 MB）は「この視点にネットワークで払ってよい
バイト数」なのに、**採否のループが取得済みのノードも数えていた**。
結果、寄っても予算が既に持っているぶんで埋まり、**ズームインしても点が増えなかった**。

| zoom | 修正前 | 修正後 |
|---|---:|---:|
| 17.2 | 125,384 点 / 5 ノード | **678,613 点 / 20 ノード** |
| 18.4 | — | **1,937,155 点 / 44 ノード** |
| 19.6 | 124,112 点 / 3 ノード | **1,605,021 点 / 31 ノード** |

**しかも推定が上がれない循環になっていた。** 予算が 2 MB なので要求も 2 MB で終わり、
`bandwidthBps` は「取得が走っていた時間あたりのバイト数」なので小さいまま出る
（localhost で **1.09 MB/s**）。予算を直したら同じ localhost で **81.71 MB/s** に
跳ねた。**帯域推定を疑う前に、予算がそれを絞っていないかを見ること。**

常駐しているノードは wire 0 バイトとして数える（`SelectInput.isHeld`）。
点数の予算（`maxPoints` = 200 万点）には数えるので、上限は点数側が持つ。

### 点間隔の下限は 2.0 px から 1.0 px に下げた **[実測]**

`budget.screenSpaceError` は「点間隔が画面上で何 px か」の下限で、
これより細かいノードは取らない。2.0 px は**点の大きさ（1.4 px）より広く**、
点の間に必ず隙間が空く。配信物は depth 6 まであり 8.5 cm 間隔まで持っている
（`spacing` 5.435 m、depth ごとに半分）のに、2.0 px では
zoom 18.5 でも depth 2 = **点間隔 1.36 m** で打ち切っていた。

| depth | ノード | 点 | MB | 点間隔 |
|---|---:|---:|---:|---:|
| 0 | 1 | 12,174 | 0.14 | 5.435 m |
| 3 | 27 | 1,273,834 | 11.05 | 0.679 m |
| 5 | 357 | 16,027,803 | 113.26 | 0.170 m |
| 6 | 1,097 | 15,335,283 | 108.61 | 0.085 m |

既定は 1.0 px。`?sse=` で上書きできる。

### 正射投影では LOD の式と可視判定が別物になる **[実測]**

軸方向のプリセット（`平面` / `南↑` / `西→` / `北↓` / `東←`）は正射に切り替わる。
そこで 2 つ壊れていた。**どちらも「絵を見ても気づけない」ではなく、
片方は点群が丸ごと消えるという派手な壊れ方だった**（気づかなかったのは
軸方向で点群を出す経路を誰も踏んでいなかったため）。

**1. 可視多角形の幅が 0 になり、点群が全部落ちていた。**
`Viewer.groundCorners()` は画面 4 隅の光線と z=0 の交点を取るが、
`t > far`（= `distance * 4`）なら「地平線の上を向いている隅」として `far` で止める。
正射は**光線が平行で、近平面を `-100_000` に置いてある**ので `t` が 10^5 の桁になり、
4 隅すべてが同じ点に潰れていた。実測（pitch 84° / zoom 17.2）:

| | 可視多角形の東西 | 南北 | 点群 wanted |
|---|---:|---:|---:|
| 俯瞰 52°（透視） | 1,991 m | 2,013 m | 182,106 点 |
| 横から 84°（**正射・修正前**） | **0 m** | 1,184 m | **0 点** |
| 横から 84°（透視に切替） | 3,733 m | 4,032 m | 124,550 点 |
| 横から 84°（**正射・修正後**） | — | — | **124,550 点** |

正射では `far` で切らない。透視の「地平線より上」の分岐は残す。

**2. SSE が距離で割られていた。** 透視の式
`spacing x (画面高 / 2) / (距離 x tan(fovY / 2))` は、正射では
`spacing / metresPerPixel x (ノード距離 / カメラ距離)` に相当する。
正射は 1 px が何メートルかが画面のどこでも同じなので、**距離に依ってはいけない**。
実測（zoom 17.2 / 900 px、視線方向に帯 800 m）で端から端の偏りは
**3.0 倍 = 1.6 LOD 段**。手前は過剰に細かく、奥は過剰に粗く選ばれていた。
`ViewState.orthographic` と `metresPerPixel` を渡して
`sse = spacing / metresPerPixel` に切り替える。

### 帯域推定は「回線の容量」を測る **[実測]**

直近 4 秒の完了分を合計し、**その間に実際に取得が走っていた時間**（区間の和集合）で割る。
並列に走った分はここで足し合わされる。待ち時間で割らないのは、アイドルを挟むと
容量を過小に見積もるため。

**1 リクエストごとに `wireBytes / 所要時間` を測ってはいけない。** 11 本並列なら
1 本あたりは 1/11 に見える。旧実装がこれで、実効の 1/5 以下しか出ておらず、
**点群の LOD 予算は下限に張り付いていた**。回帰は `perf/bwcheck.mjs` が見る
（実効帯域が分かっているプロファイルで推定と突き合わせる）。

速い回線ほど低めに出る（`fatpipe-highrtt` で 0.55 倍）。和集合の中に
「1〜2 本しか飛んでいない待ち時間」が入るためで、**過小に倒れるので
予算を甘くする方向には効かない。**

### 予算は増える方向にだけ組み直す

`budget()` を評価するのは点群の起動時とカメラ移動時だけだった。
**カメラを動かさなければ、推定が最も当てにならない起動直後の値が最後まで残る。**
1 秒ごとに見て、1.5 倍を超えて増えたときだけ組み直す。

**減る方向には組み直さない。** 選び直すと常駐していたノードが捨てられ、
取得済みのバイトが無駄になる。実測で、下げ直すと転送が増えるのに常駐点数が減った。
視野が変わったときは別で、カメラ移動の経路が改めて評価する。

**カメラは `domain/camera.ts` でローカル ENU メートルに直してから渡す。**
地図の `cameraToCenterDistance` は px 単位で、しかもキャンバス高さと fov だけで決まり
**ズームに依存しない**。これをそのまま高度として使うと視点が定数になり、
LOD が「近くは細かく遠くは粗く」を一切やらなくなる。

常駐点数の上限は描画コストから決める。実測値は `docs/web_results.md`。
**`Points` は 6.0 M 点まで 60 fps を保つ**（deck.gl `PointCloudLayer` は 3.0 M で 68〜82 ms）。
既定は 200 万点。測った上限をそのまま採らないのは、計測が開発機で、
配信先の GPU が分かっていないため [未確認]。
`three/pointsRenderer.ts` はノード 1 つを `Points` 1 つで持ち、ジオメトリは
decode の返り（Transferable）をそのまま `BufferAttribute` にする。

**セッタは値が変わったときだけ通知する。** 通知は `main.ts` の `refresh()` を呼び、
`refresh()` はセッタを無条件に呼ぶので、素直に毎回通知すると相互再帰で
`RangeError: Maximum call stack size exceeded` になる（`?pc=1` で実測）。

### decode pool

`min(4, max(1, hardwareConcurrency - 2))` 本の Worker。各 Worker が laz-perf(WASM) を 1 つ持つ。
返りは Transferable。

`positions` は **AOI ローカル原点からの相対 [m]** にする。EPSG:6674 の値は −6 万台なので、
Float32 に world 座標を入れると 0.5 m 級の微地形が丸まる。原点と回転行列は
`catalog.json` の `local_frame` に持つ。描画側はローカル原点をワールド原点として扱う。

## リクエストスケジューラ

すべての取得が 1 つの choke point を通る（`net/scheduler.ts`）。
3D Tiles も COPC も地形タイルも例外を作らない。

```
カメラ / 視野
   ↓ epoch++
LOD・可視判定（純関数、IO しない）
   ↓ リクエスト
Scheduler ─ 優先度キュー / 並列上限 / byte budget / coalescing
          ─ cancellation / memory LRU / retry
   ↓
Range fetch（ストリーム読み、受信バイトを逐次カウント）
   ↓
decode worker pool → GPU
```

### 優先度クラス

| P | class | 中身 | 群 |
|---:|---|---|---|
| 0 | `catalog` | `catalog.json` | a |
| 0 | `terrainCoarse` | 視野を覆う**最小ズーム**の地形タイル | a |
| 1 | `terrainFine` | 同じ視野の高ズームタイル | b |
| 1 | `pcIndex` | COPC の header と hierarchy | b |
| 2 | `semantics` | `objects.geojson` | c |
| 2 | `plateau` | 可視の b3dm | c |
| 3 | `pcCoarse` | 点群の粗ノード | d |
| 4 | `pcFine` | 点群の細ノード | d |
| 5 | `prefetch` | 先読み（点群の被覆輪郭など） | e |

設計上の要点が 2 つある。

**`objects.geojson` を P0 に置かない。** 地物のクリック情報は初回描画に要らない。
細い回線では単発の数百 kB が `first_meaningful_render` を丸ごと押し出す。

**FMR が立つまで `pcCoarse` / `pcFine` は発行しない。**
これが「解析結果は点群の全ロードを待たずに出す」の実装上の担保。
`pcIndex` だけは先に取り、FMR 直後に LOD を回せるようにしておく。

### 並列上限

`PerformanceResourceTiming.nextHopProtocol` で h1 か h2 かを判定して切り替える。

| | 全体 | a | b | c | d | e |
|---|---:|---:|---:|---:|---:|---:|
| h1 | 6 | 4 | 4 | 3 | 3 | 1 |
| h2 | 12 | 6 | 6 | 4 | 6 | 2 |

h2 でも無制限にしない。多重化してもボトルネックが帯域なら
**低優先のバイトが高優先のバイトを押し出す**。多重化は優先度制御の代わりにならない。

数値はすべて初期値であって根拠は無い。実測でチューニングする前提のものである。

### range coalescing

LOD が選んだノードを `pointDataOffset` でソートし、gap と合計サイズが閾値内なら
1 本の Range にまとめる。COPC のノードはファイル上でほぼ連続して並ぶので、
まとめても「読むが使わないバイト」はほとんど出ない。

R2 はマルチレンジを受け付けない（`docs/platform.md`）ので、**連続 1 本への結合だけ**。
飛び地は結合できない。

**まとめた range は届いた分から順にノード単位でデコードする**
（`FetchTask.parts` / `onPart`）。1 本の完了を待つと、まとめたことが
そのまま「最初の点が出るまでの遅延」になる。**この 2 つはセットでないと意味を持たない。**

### cancellation

視野から外れた要求を切る。切ってよいのは次の 3 つをすべて満たすときだけ。

1. 発行時より epoch が進んでいる
2. `stillNeeded()` が偽（= いま必要とされていない）
3. 受信が 8 割未満（8 割超なら捨てるほうが損）

**epoch が古いだけでは切らない。** 連続パン中は毎フレーム epoch が進むので、
それだけを条件にすると 9 割受信済みの要求まで捨てる。
LOD の再計算は 60 ms デバウンスで回し、epoch もそこで進める。

順序にも制約がある。**点群の `stillNeeded()` は LOD の結果を見る**ので、
LOD を更新する前に reap すると古い集合を見て「まだ必要」と答えてしまう。
地形は可視判定が地図を直接見るのでこの制約が無い。

受信済みバイトはストリーム読みで数える。`Content-Length` を丸ごと無駄と数えると過大になる。

### retry と cache

- ネットワークエラーと 5xx は最大 2 回、指数バックオフ（ジッタつき）
- 4xx は再試行しない
- **Range を要求したのに 200 が返ったらエラーにする。** 黙って全体を落とすのが
  最大のネットワーク事故で、しかもクライアントは正常に見える（`docs/platform.md`）

| 層 | 実体 | 目的 |
|---|---|---|
| L0 | in-flight map | 同一キーの重複要求を合流させる |
| L1 | メモリ LRU（バイト上限） | カメラ往復での再取得・再デコードを避ける |
| L2 | HTTP キャッシュ | `immutable` + 内容ハッシュつき URL |

cold cache で測るときは L2 を明示的に消す。

## アセットの形式

| asset | 形式 | 配信 |
|---|---|---|
| catalog | `catalog.json` | 1 GET。全アセットの URL・zoom 範囲・ジオイド高・ローカル原点 |
| 地形 + `h_conn` | **RGBA PNG タイル**（自前パッキング） | XYZ。条件ごとに 1 ピラミッド |
| PLATEAU 建物 | 3D Tiles 1.0（AOI サブセット） | tileset.json + b3dm |
| 地物 + assertion | `objects.geojson` | 1 GET（edge で br 圧縮） |
| 点群 | **COPC** | Range |

### RGBA タイルのパッキング

**1 タイル = 1 条件**。RGB に標高、A に `h_conn` を入れる。

```
RGB : Terrarium 方式   elev_m = (R*256 + G + B/256) - 32768     精度 1/256 m
A   : h_conn コード    A == 0        → どの水位でも浸水しない
                       A in [1,255]  → h_conn = (A-1) * h_step  (h_step = 0.05 m)
nodata(elev) : R=G=B=0 を予約
```

Terrarium を選ぶのは 1/256 m の分解能のため。Mapbox terrain-RGB の 0.1 m 刻みでは、
問題にしている 0.25 m 級の差に対して量子化が粗い。

同じ PNG に入れるので **標高と `h_conn` が必ず同一画素で整合**し、リクエストも半分になる。

**差分ピラミッド**（`diff*`）は R=左条件の `h_conn` コード / G=右条件 / B=左条件の地盤高コード
/ A=255。**水みちピラミッド**（`flow_*`、`catalog.flow`）は R=log スケールの集水（8bit）
/ B=充填深コード / A=有無。どちらも色だけを与えるので、地形メッシュの形は元条件の
タイルから取る（`domain/terrain.ts` / `domain/flow.ts`。上「水みちと窪地をどう出したか」）。

**このタイルを地図ライブラリの `raster-dem` 相当に渡してはいけない [既知]。**
通常のイメージデコード経路を通るとアルファが乗算され、
A < 255 の画素（＝ほぼ全ての浸水域）で RGB が壊れて標高が狂う。
陰影を自前シェーダで計算しているのはこれを避けるためでもある。

GPU に上げる分には問題ない。`createImageBitmap(blob, { premultiplyAlpha: 'none',
colorSpaceConversion: 'none' })` で読み、テクスチャは非乗算のまま渡す。
`mipmaps: false` と nearest フィルタも必須で、パックした値を線形補間すると別の標高になる。

### 3D Tiles

配布物をそのまま使う。ただし切り出し時に **batch table を使うキーだけに絞る**
（`scripts/82`）。PLATEAU の全属性は 70 キー近くあり、viewer が読むのは
`gml_id` と塗り分け用の 2 キーだけである。glTF チャンクはバイト列のまま移すので
ジオメトリも見た目も変わらない。

b3dm には色が無い（texture・頂点色・`baseColorFactor` すべて無し）ので、
属性で塗り分けるには **primitive を色ごとに分割して material を与える**
（`view/plateau.ts`）。draw call はタイルあたり「出現した色数」まで増える。

## CPU 側でタイルを読む

断面図（`ui/section.ts`）は、測線に沿って標高と `h_conn` を CPU 側で読む。
**追加の通信は起きない。** 画面に出ているのと同じタイルを scheduler 経由で取るので、
取得済みならメモリキャッシュから返る。

**canvas を経由してはいけない [実測]。**
2D canvas はアルファ乗算した状態で画素を保持するので、`drawImage` → `getImageData` の
往復で A < 255 の画素の RGB が壊れる。`h_conn` コードはほぼ常に 255 未満なので、
ほぼ全画素が壊れる（標高 1.5 m の画素が 32512 m として読めた）。
`premultiplyAlpha: 'none'` で作った `ImageBitmap` でも、canvas に描いた時点で同じである。

`assets/png.ts` に 8bit RGBA / 非インタレース PNG の復号を持つ。
展開はブラウザ内蔵の `DecompressionStream('deflate')` を使うので依存は増えない。
**GPU に上げる経路（`decodeTileImage`）と CPU で読む経路（`decodeRgba8`）は別物**で、
前者は canvas を通らないので従来どおりでよい。

断面の塗りは **`h_conn <= H` を満たす区間だけ**にする。標高が水位より低いだけでは塗らない。
連結していない窪地を塗ると、このリポジトリの主張と逆のことを言うことになる。

## 何を遅延ロードするか **[実測]**

**チャンクの大きさと 1 往復を天秤に掛ける。** 高 RTT では 1 往復が 400〜570 ms かかる
（`slow-highrtt` / `fatpipe-highrtt` はどちらも RTT 400 ms）ので、
**それより小さいチャンクを切り出すと損をする。**

| チャンク | br | 遅延する |
|---|---:|---|
| `plateauTiles`（b3dm パース + 3D Tiles） | 61 kB | する |
| `lazy`（点群 index / LOD / decode 管理） | 27 kB | する |
| `decode.worker`（laz-perf） | 24 kB | する（Worker） |
| `semanticsMesh`（三角形化） | 1.8 kB | **しない** |

`semanticsMesh` は一度遅延していた。守っていたのは `objects.geojson` の
`JSON.parse`（3 ms）で、**払っていたのは往復 568 ms** だった
（`docs/web_results.md`「objects.geojson のパースコストは 3 ms」）。

## 計測のしかけ

### FPS は指標にしない

測るのは「いつ・何バイトで・何が見えたか」。計測パネルは既定で非表示で、
`?perf=1` か `P` キーで開く。`PerfRecorder` は常に動いているので、
パネルを閉じていてもハーネスが読む値は変わらない。

### マイルストーンの定義

曖昧さを残さないことが要点である。

| name | 定義 |
|---|---|
| `app_start` | `performance.timeOrigin` |
| `catalog_loaded` | `catalog.json` のパース完了 |
| `first_meaningful_render` | **視野を覆う最小ズームの地形タイルが GPU に乗り、浸水色が 1 フレーム描かれた**時刻。高ズームの到着は待たない |
| `time_to_terrain` | 細メッシュが視野を満たした |
| `time_to_plateau` | tileset の 22 タイルが揃った。**塗り替え（属性色の切り替え）では測り直さない**。初回描画の指標 |
| `time_to_first_useful_pc` | **LOD がその視点に必要と判断した点数の一定割合**が常駐した |
| `time_to_pc_refined` | 選ばれたノードが出揃った |
| `camera_settle_latency` | カメラ停止 → 新しい視点の地形と粗ノードが常駐するまで（細ノードは待たない） |

`time_to_first_useful_pc` を絶対点数ではなく割合で定義するのは、
データ密度と LOD 予算を変えるたびに意味が変わるのを避けるためである。

### 収集する量

| 量 | 取り方 |
|---|---|
| 転送バイト | `PerformanceObserver('resource')`。**wire（回線を流れた量）で数える** |
| shell コスト | 同上を code/font と data に分けて数える。FMR を決めているのはコード側なので、毎回見る |
| リクエスト数・並列ピーク | scheduler がクラス別に数える |
| キャンセルと無駄バイト | scheduler。無駄は **abort までに実際に読めたバイト** |
| decode 時間 | Worker 内で測って postMessage に載せる |
| `nextHopProtocol` | h1/h2 の判定と結果の解釈に使う |

**バイトはデコード後ではなく wire で数える。** br が効くアセットでは大きくずれる。
Cloudflare は br 応答に `content-length` を付けない（`docs/platform.md`）ので、
`PerformanceResourceTiming.encodedBodySize` を URL と開始時刻で引き当てる。
引き当てられない場合はデコード後の値に戻す。**過大に出る方に倒す。**
小さく見せる方に倒すと判断を誤る。帯域推定にも同じ値を使う。

クロスオリジンだと `transferSize` も `encodedBodySize` も 0 になるので、
**同一オリジンで配信する**（`docs/infra.md`）。これは計測の都合であると同時に、
**外部に出られない回線で動くための条件**でもある。`deploy/check.mjs` の MUST
「外部オリジンへのリクエストが 0 件」がここを守る（ブラウザを立てて数える。
`fetch` では分からない）。

### 正しさを守るテスト

性能とは別に、**画面に出ている値が解析と一致するか**を検査する。

| テスト | 内容 |
|---|---|
| `test/parity.test.mjs` | タイルの RGBA パッキング往復。地物の `depth` と判定が Python 側と一致するか |
| `test/pair.test.mjs` | **比較のペア**（`comparisonPair`）と、ペアに対する判定の件数。地形の色と地物の色が同じ比較を見ていることを固定する。**片方だけ違う条件を見ていても「それらしい絵」が出るので、目では捕まらない** |
| `test/camera.test.mjs` | カメラ → ローカル座標の換算（純関数） |
| `test/png.test.mjs` | 自前 PNG 復号が Pillow と全画素一致するか |
| `perf/bwcheck.mjs` | 帯域推定が実効帯域と合っているか（絞りが既知のプロファイルで突き合わせる） |
| `perf/frustum.mjs` | 視野判定が台形になっているか（pitch 0 で外接矩形と一致するのが確認） |
| `perf/tileorient.mjs` | **画面の画素**と焼いたタイルの同じ座標の値が一致するか |
| `perf/waterlevel.mjs` | 水位を変えると浸水域が単調に増え、かつリクエストが増えないか |

前の 3 つは「値が正しいか」しか見ない。**「その値が画面のどこに出ているか」**は
`tileorient.mjs` が見る。値の検査だけでは、南北反転も半セルずれも捕まらない。

`waterlevel.mjs` が 2 つの性質を同時に見るのも同じ理由である。
「リクエストが増えない」だけを見ると、**何も起きていなくても通ってしまう。**

### ネットワークプロファイル

Playwright + CDP `Network.emulateNetworkConditions`。本リポジトリの定義で、
Chrome DevTools のプリセットそのものではない。

| profile | down | up | RTT | 用途 |
|---|---|---|---|---|
| `normal` | 無制限 | 無制限 | 0 ms | 上限 |
| `fast4g` | 4 Mbps | 3 Mbps | 70 ms | 一般的なモバイル |
| `slow-highrtt` | 1 Mbps | 0.5 Mbps | 400 ms | 細い回線 |
| `fatpipe-highrtt` | 20 Mbps | 5 Mbps | 400 ms | **往復回数の影響を帯域から切り離す** |

各プロファイルで cold cache から測る。計測時の注意（headed で測る、1 回で判断しない、
wire で数える）は `docs/web_results.md`。

ローカルの `web/serve.mjs` は production 相当の条件を再現する
（HTTP/2 と HTTP/1.1 の切替、Range 206、事前圧縮、immutable、マルチレンジは 400）。
**開発サーバでネットワークを測っても意味が無い。**

## 配信の境界

ブラウザから見た境界は **`catalog.json` が指す URL** の 1 点だけである。
アセットがどこに置かれていても、catalog の URL が相対のままなら
アプリ側に分岐は要らない。

Cloudflare 側の構成（静的アセットは Workers Assets、COPC だけ Worker → R2）は
`docs/infra.md`、プラットフォームの挙動は `docs/platform.md`。

PDAL / GDAL / COPC 生成 / ラスタ処理は Workers では動かさない。
CPU 時間とメモリの制約に合わず、既存の Python パイプラインをそのまま使えなくなる。

LAS のアップロード経路（ブラウザ → R2 直接 multipart）はまだ作っていない。
設計上の要点は「API サーバを経由させない」ことで、詳細は `docs/todo.md`。

## レンダラを差し替える条件

`PointCloudRenderer` インターフェースを挟んである。deck.gl `PointCloudLayer` から
three.js の `Points` への差し替えは**この境界だけで済んだ**（`CopcIndex` /
`LodSelector` / `Scheduler` / `DecodePool` は 1 行も変えていない）。
4 つをレンダラから分離してあるのはそのためである。

いま `Points` で足りていない兆候は無い（常駐 12,174 点 / draw call 1）。
次のいずれかが実測で成立したら、さらに自前のレンダラに移す。

| # | 条件 | なぜ限界の徴候か |
|---|---|---|
| 1 | 予算内の常駐点数でドラッグ中の frame time が 16.7 ms を超える | `Points` は 1 点 1 頂点なのでここが出たら本当に点数の問題 |
| 2 | EDL・密度連動の点サイズ・ノード単位のフェードイン・ノード内 progressive refinement のいずれかが要る | `PointsMaterial` で表現できない |
| 3 | GPU メモリ上限に当たり、自前の LRU eviction が要る | いまはノード単位の `dispose()` で足りている |

## 既知の制約

| 事項 | 区分 | 内容 |
|---|---|---|
| **ズームの基準が 256 px と 512 px で 1 ずれる** | **[実測]** | 上記「ズームの規約」。画面は成立してしまうので、`perf/tileorient.mjs` と `perf/zmix.mjs` で要求タイルの z ごと照合する |
| b3dm の `_BATCHID` は size:1 の属性で来る | **[実測]** | loaders.gl が `CUSTOM_ATTRIBUTE_2` に改名するので**名前ではなく `size === 1` で拾う** |
| glTF は Y-up、3D Tiles は Z-up | **[既知]** | loaders.gl は変換せず `rotateYtoZ` を立てて渡してくる。受け側で回す |
| 点群レンダラのセッタが毎回 `onChange` を出すと相互再帰する | **[実測]** | `refresh()` ⇄ セッタで `Maximum call stack size exceeded`。値が変わったときだけ通知する |
| **loaders.gl は Draco を外部 CDN から取る** | **[実測]** | 既定で `unpkg.com` と `www.gstatic.com` に worker 1 本あたり 1 組（実測 3 本 / 計 1.15 MB）。**外部に出られない回線では建物が 1 棟も出ない。** `scripts/vendor-draco.mjs` が `public/vendor/draco@<version>/` に複製し、`options.CDN` をそこへ向ける。`options.modules` に URL を渡す道は worker へ渡る途中で落ちて効かない |
| RGBA パッキングのアルファ乗算 | **[既知]** | GPU 経路は `premultiplyAlpha: 'none'`、CPU 経路は canvas を通さない |
| `EXT_disjoint_timer_query_webgl2` の可用性 | **[未確認]** | 無ければ CPU 側の壁時計で代用し、その旨を結果に明記する |
| 正射投影での点群 LOD の screen-space error | **[未確認]** | `sse` の式は透視のカメラ距離を前提にしている。正射では距離が効かないので、軸方向プリセットのときの採否は検証していない |
