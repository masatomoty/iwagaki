# DESIGN — 解析の設計

舞鶴市 吉原地区について、**同じ高潮水位に対して、地形データを変えると浸水判定が
どこで変わるか**を地物単位で求める。その解き方を決める文書。

**前半が要求、後半が実装。** 前半は実装が変わっても変わらない部分
（何を満たさなければならないか、なぜそう解くか）。後半はいまのコードがどうなっているか
（スクリプト名・パラメータの実値・成果物の形式）。
**実装を変えるときは、前半の要求を壊していないかを先に確かめる。**

入力データの素性は `docs/data.md`、結果は `docs/results.md`、
ブラウザ側は `docs/web_design.md`。

根拠区分は `docs/data.md` と同じ（**[実測]** / **[既知]** / **[仮説]** / **[未確認]**）。

---

# 要求

## 出力は「判定が変わる場所」である

浸水ハザードマップを作るのではない。**地形データを差し替えたときに、
どの建物・どの道路で判定がひっくり返るか**を示す。

したがって、

- 少なくとも 2 つの地形条件を**同一の設定で**回し、差を取れること
- 差を面積ではなく**地物 ID に紐づけて**出せること
- 「変わらなかった」も結果として出せること

面積の合計が同じでも場所が入れ替わっていれば、それがこの解析の答えである。

## PLATEAU を書き換えない

点群や DEM から PLATEAU の geometry を作り直さない。
**PLATEAU の ID に対して assertion を外付けする。**

```
PLATEAU Entity  (bldg:Building / tran:Road)
  ├─ geometry / semantics      … PLATEAU が持つ。ID・用途・構造・道路種別
  ├─ Terrain Observation       … DEM / 点群。現況の地表面
  └─ Derived Assertion         … 本リポジトリが生成する
       ├─ ground_elev          地盤高 [m T.P.]
       ├─ h_conn               連結浸水開始水位 [m T.P.]
       ├─ depth(H)             任意水位 H での浸水深
       └─ decision             判定クラスと条件間の差異
```

出力は `gml_id` をキーにしたテーブルと GeoJSON であり、CityGML は変更しない。
上流が更新されても、こちらの成果物は ID で貼り直せる。

## 浸水の決め方は 2 つあり、既定は単純な方

| モデル | 式 | どこで既定か |
|---|---|---|
| **単純** | `浸水深 = max(0, 潮位 − 地盤高)` | **viewer の既定**（2026-08〜） |
| **連結** | 上に加えて `h_conn ≤ 潮位`（海から地表面をたどって到達できる） | **解析**（`scripts/30〜50`）と `docs/results.md` の数字 |

### 連結モデル（解析側）

**海側の開放水面から連結して到達できるセルだけ**を浸水とする。連結していない窪地を
浸水させると、微地形の効果を評価する目的と矛盾する。手法としては coastal flooding の
文脈で "hydrologically connected bathtub model" として確立されたもの
（Poulter & Halpin 2008 ほか、NOAA Sea Level Rise Viewer も同系統）**[既知]**。
本件はその適用であって新手法の提案ではない。

### なぜ viewer の既定を単純な方にしたか

**連結モデルが現場の観測と合わなかった。** 舞鶴市から東舞鶴について
「0.8 m の潮位でも浸水する範囲があるはずなのに着色されない」「地盤高 0.8 m のところで
潮位 0.9 m にしても浸水深が 0 のまま」との指摘があり（2026-08）、調べると
**モデルの答えとしては正しかった**（市街は護岸天端 1.0〜1.3 m に囲まれた
0.8〜1.0 m の窪地。「既知の限界」2）。こちらからは、精緻化には排水区・側溝底高・
逆流防止構造の有無が要ると照会した。回答は

> ご指摘の通り、精度高いシミュレーションをするためには上記のデータが必要になります。
> が、現状整理できていないというのが課題です。
> 現場にいる経験則として、市内全域的に、排水路などを通じて、潮位よりも地盤高が
> 低い箇所は、その差だけ浸水している状況です。
> 現時点では、単純に「潮位ー地盤高＝浸水深」として可視化することで問題ない

だった。**連結性を補正するデータが無く、しかも現に逆流が起きている**以上、
地表面の連結だけを見て内陸を 0 に潰すのは「厳密」ではなく単に外している。
だから viewer の既定は単純モデルにし、連結モデルは切り替えで残す。

**捨てたものは無い。** `h_conn` は引き続き解析側が焼き、配信タイルの A チャネルに
入っている（`docs/web_design.md`）。単純モデルは同じタイルの RGB（標高）だけを見る
ので、**配信物は 1 バイトも変わらず、切り替えは uniform 1 個で済む。**
`docs/results.md` の数字は連結モデルのものである。

排水路の吐口高・フラップゲートの有無が手に入ったら、**精緻化するのは連結モデル側**
（`h_conn` の seed に吐口を足す）であって、単純モデルはその間の暫定である。

## 任意の水位を定数時間で評価できること

水位 H を掃引するたびに flood fill を回さない。セルごとに
**「そのセルが海と連結して浸水し始める最小の水位」 `h_conn` を 1 回だけ求める。**

`h_conn` が well-defined なのは、浸水候補集合 `{E <= H}` が H について単調増加で、
連結性も単調に保たれるため。
`h_conn(c) = min over paths seed→c of max(E along path)`（bottleneck / minimax path）であり、
Priority-Flood 系アルゴリズムと同じ量である。

これを持つと:

| | 効果 |
|---|---|
| 出力 | 地形条件ごとに **ラスタ 1 枚**で全水位を表現できる |
| 評価 | `wet(H) = h_conn <= H`、`depth(H) = max(0, H - E)` の 2 式だけ |
| 地物 | 地物ごとに `h_conn` と `ground_elev` を持てば、任意 H の判定が定数時間 |
| 比較 | 条件間の `h_conn` の差が、そのまま**その地点の判定が変わる水位帯** |

**配信物の量が水位の数に依らない**のもここから来る。水位ごとに浸水域を焼くと
成果物が水位刻みの数だけ増えるが、`h_conn` なら 1 枚で済む。

## データ源の差と解像度の差を分離できること

「差が出た」だけでは、**元のデータが違うから**なのか**細かくしたから**なのかが分からない。
両者を分けるために、**高解像度地形を粗く集約しただけの対照条件**を必ず用意する。

- 粗地形 と 対照 の差 = **データ源**の差
- 対照 と 高解像度 の差 = **解像度**の差

この対照条件が無いと、この解析は何も主張できない。

## 条件間で揃えなければならないもの

比較が条件そのものの差以外に汚染されないよう、次は全条件で同一にする。

| 揃えるもの | 揃えないと何が起きるか |
|---|---|
| **seed（開放水面）** | 地形ごとに seed が変わり、比較が seed の差になる。**高解像度地形から 1 度だけ求めて共有する** |
| 連結性（4 / 8 近傍） | 水の通り方が変わる |
| 水位の範囲と刻み | `h_conn` の量子化が変わる |
| nodata の扱い | 障壁になるか通路になるかで連結性が変わる |

設定は出力メタデータに必ず記録する。あとから「どの設定で回したか」を追えないと、
結果を再現できない。

## 地盤高は信用できるところから取る

DEM は建物を除去して補間した成果なので、**footprint の内部は補間値**であり
実際の地盤ではない。建物の地盤高を footprint 内部から取ってはいけない。

同様に、**路面が地表面と一致しない地物**（橋梁・高架橋・アンダーパス・トンネル）と
**大半が開放水面に重なる地物**は、DTM 由来の地盤高が意味を持たない。
これらは除外できなければならない。除外しないと、橋の上の道路が
「水面の標高を地盤とする」形で偽陽性の上位に並ぶ。

## 差が出たと言うための指標

「地形を変えたら判定が変わった」と主張するには、
**何をもって変わったとするか**を先に決めておく必要がある。

| 指標 | 意味 |
|---|---|
| 判定が変わった地物の数 | 代表水位ごと |
| 新たに浸水 / 浸水しなくなる面積 | 面積としての入れ替わり |
| `delta_h_conn` の p5 / p50 / p95 | 判定が変わる水位帯の広さ |
| 対照条件 と 高解像度 の差 | **解像度だけ**で生じる分 |

**差が無いと判断する条件**: どの水位でも判定が変わる地物が 0、または差が
DEM の高さ精度（**[未確認]**、目安 0.25 m）以下のノイズに収まる場合。
そのときは AOI を変える（より低平な河口部）か、水位刻みを見直す。

## ブラウザ側への要求

解析結果を「地物単位で判定が変わる場所」として見せるために、ブラウザ側が満たすこと。
実装と実測は `docs/web_design.md` / `docs/web_results.md`。

- 水位スライダ。参照水位（MSL・朔望平均満潮位・既往最高潮位ほか）に目盛りを置く
- 地形条件の切替と、条件間の差分表示
- 点群の ON/OFF
- 建物・道路をクリックすると、条件ごとの `ground_elev` / `h_conn` / 浸水深 / 判定を出す
- **断面**。この解析が問うているのは「護岸の天端を水位が越えるか」であり、
  0〜3 m の起伏は俯瞰では潰れて読めない。横から見て水平線を引ける手段が要る
- **水位を変えてもサーバ往復も再計算も発生しない。** `h_conn <= H` を評価して
  `max(0, H - E)` を描くだけにする。これは `h_conn` を持っていることの直接の帰結であり、
  UI の都合ではなく設計の要請である

## やらないこと

- 本格的な CFD / 2 次元浅水方程式ソルバ（越流量・時間発展・河川流入は扱わない）
- 独自 ICP / NDT による点群レジストレーション
- 点群 segmentation AI
- CityGML の自動更新・書き戻し
- 大規模 GIS バックエンド（DB・タイルサーバ・API）
- 全舞鶴市の処理
- 過度な UI 作り込み、レイヤ管理 UI、時系列アニメーション、印刷レイアウト

**内水・地表流の集中**（flow accumulation・窪地構造）は、外部プロダクト FARR の
ロジックに倣って `scripts/33_flow_accum.py` が**潮位非依存の静的ラスタ**として焼く
（Priority-Flood + ε ／ D8、`docs/data.md` §7）。ただしこれは **`h_conn`・浸水判定とは
独立した別オーバーレイ**であり、判定モデルには混ぜていない。地形条件を差し替えたときに
「水みち・窪地構造がどう変わるか」を、浸水判定と同じ 4 条件で見るための材料である。

既存の GIS / 点群 OSS で解ける問題は、**先に調べて再発明を避ける**。
何を使っているかは実装側に挙げる。

## 既知の限界

成果物に必ず明記する。

1. **静水位モデル**であり、越流の時間発展・流量・波の打ち上げを含まない。
2. **地下構造物・暗渠・排水路を考慮しない。** 実際の連結性はこれらに強く依存する。
   **水門・樋門は吉原入江に無いことが確認できた**（市への照会、2026-08。`docs/data.md`）。
   残るのは排水路で、**吐口にフラップゲートが無い**ため潮位が上がれば逆流しうる。
   本モデルは地表面の連結性しか見ないので、**内陸側を過小に評価している可能性がある**
   （以前ここには「閉まっていれば越流水位が上がる」= 過大評価の側だけ書いていたが、
   閉鎖構造が無いと分かった以上、効くのは逆向きである）。
   吐口の位置と敷高は市が来年度に調査委託を出す予定。
   **これは「可能性」ではなく実際に効いていることが東舞鶴で確認できた**（2026-08-25）。
   市街は護岸天端 1.0〜1.3 m に囲まれた 0.8〜1.0 m の窪地で、潮位を
   0.45 → 0.95 m と 0.5 m ぶん上げても**市街で新たに浸かるのは 1.37 ha だけ**、
   次の 0.3 m（1.00 → 1.25）で 14.23 ha 増える [実測]。既往最高潮位 0.93 m では、
   連結して浸水する 15.75 ha に対し「標高は潮位より低いが連結しない」土地が
   **10.57 ha（321 地物・建物 201 棟）**ある。
   viewer は当初これを**窪地**として別の印で出し、判定には混ぜなかった。
   **その後、市の回答（2026-08）を受けて viewer の既定を単純モデル
   （潮位 − 地盤高）に変えた**ので、この 10.57 ha は既定では浸水域そのものとして
   塗られる（上の「浸水の決め方は 2 つあり、既定は単純な方」）。
   窪地という区分は「海からつながる」を選んだときにだけ現れる。
3. 京都府 DEM は**森林資源把握を目的**とした成果であり、市街地の精度は保証されていない
   （`docs/data.md`）。建物跡地の補間値は特に信頼度が低い。
4. 計測年次が **2019〜2023** のいずれか不明（**[未確認]**）。
   PLATEAU（2026-03 作成）との時期差がある。
5. 高潮水位は**指定ハザードではなくパラメータ**である。ただし
   **舞鶴は高潮浸水想定区域（水防法第 14 条の 3）に指定されている**（令和 8 年 2 月、
   京都府。`docs/data.md`）。京都府の想定は 910 hPa（室戸台風規模）で、
   基準潮位 T.P.+0.69 m（朔望平均満潮位 0.545 ＋ 異常潮位 0.142）に高波の越波を加え、
   **堤防等は決壊するものとして扱っている。** 本リポジトリのモデルは施設を一切持たないので
   決壊側の想定に近いが、これは偶然の一致であって施設を無視してよい理由にはならない。
   公表区域図（ラスタ PDF、GIS 配布なし）の図郭は判読済みで、AOI は図番号 4〜5 に掛かる
   見込み（`docs/data.md`「図郭の対応」）。面的な突き合わせは未実施（`docs/todo.md` 中 1）。
6. `h_conn` の分解能は水位刻みに量子化される。

# 実装

## パイプライン

```
[取得]                      [地形生成]                    [浸水]           [比較・結合]
京都府DEM 0.5m tiles ──┬──→ dtm_highres_050.tif ───┐
                       ├──→ dtm_control_500.tif  ──┤
                       │    (0.5m を 5m に集約)     │
地上点群 LAS ──────────┴──→ dtm_pointcloud_050.tif ┼─→ h_conn_*.tif ─┬─→ objects.geojson
   (DEM に地表面を融合)                             │                 │   objects.csv
PLATEAU dem GML ──────────→ dtm_baseline_500.tif ──┘                 │   changed_H*.geojson
                                                                      │
PLATEAU bldg/tran GML ────────────────────────────────────────────────┘   summary.json
```

すべてオフライン前処理。成果物は静的ファイルで、ブラウザ側にサーバロジックを持たない。
スクリプトは番号順に依存する（実行手順は `docs/usage.md`）。

## 座標系とグリッド

| 項目 | 値 |
|---|---|
| 解析 CRS | **EPSG:6674**（JGD2011 / 平面直角座標系 第VI系）。京都府 DEM のネイティブ |
| 鉛直基準 | **標高 T.P.**（京都府 DEM・PLATEAU dem ともに T.P.） |
| AOI | E `-61500 … -60500`, N `-60500 … -59500`（**1000 m × 1000 m**） |
| 高解像グリッド | 0.5 m → **2000 × 2000** セル |
| 粗グリッド | 5.0 m → **200 × 200** セル |

PLATEAU は EPSG:6697（経緯度）なので pyproj で EPSG:6674 に変換する。

必要な入力メンバーは `src/iwagaki/config.py` が単一の出所。
**AOI は 3 次メッシュ象限と 1/50000 図郭の境界を両方またぐ**ので、
PLATEAU `dem` は 2 ファイル、京都府 DEM は 4 タイル
（`06LC9443` / `06LC9444` / `06MC0421` / `06MC0422`）必要になる。

## 取得

配布 zip は数 GB あるが、**全部は落とさない。** HTTP Range で central directory を読み、
必要なメンバーだけ抜く（図郭コードの計算は `src/iwagaki/kokudo.py`、
Range 読みは `src/iwagaki/remotezip.py`）。PLATEAU `dem` メンバーは単体で 748 MB あるので、
ストリーム展開して AOI 外の三角形を捨てながら読む。サイズの実測値は `docs/data.md`。

## 地形の生成

4 条件を作る。

| 条件 | 中身 | 格子 | 作るもの |
|---|---|---|---|
| `baseline` | PLATEAU 地形モデル LOD1 TIN | 5.0 m | `scripts/20_build_baseline.py` |
| `highres` | 京都府 数値標高モデル 0.5 m | 0.5 m | `scripts/21_build_highres.py` |
| `control` | `highres` を平均で 5 m に集約 | 5.0 m | 同上 |
| `pointcloud` | `highres` に地上点群の地表面を融合 | 0.5 m | `scripts/17` → `scripts/19` |

**baseline**: TIN の**三角形の頂点座標だけ**を集めて 5 m 格子にスナップする。
頂点間隔が実測 5.00〜5.05 m の規則格子（`docs/data.md`）なので、三角形補間は情報を増やさない。
格子への割当率は成果物 JSON に出す。

**pointcloud**: 点群は DEM の置き換えではない。被覆が AOI の一部しかないので、
**点群がある所だけ上書きし、残りは DEM のまま**にする。地表面は 0.5 m セルごとの
最低 Z から、ラスタ領域でスパイク除去と形態学的な地面判定を通して作る
（PDAL の汎用地面フィルタは使っていない。点群が「歩いた地面を必ず見ている」性質を
使うほうが、この被覆形状では素直だった）。
**融合の前に DEM との鉛直バイアスを実測し、閾値を超えたら止める。黙って合わせない。**

## 浸水計算

`scripts/30_flood.py` / `src/iwagaki/flood.py`。

| パラメータ | 既定 | 出所 |
|---|---|---|
| 水位範囲 | 0.0 〜 3.0 m T.P. | `config.H_MIN` / `H_MAX` |
| 水位刻み `dH` | **0.05 m** | `config.H_STEP` |
| 連結性 | **4 近傍** | `config.CONNECTIVITY` |
| seed の標高閾値 | **0.20 m T.P.** | `config.SEED_LEVEL` |
| seed 成分の最小面積 | **5000 m²** | `config.SEED_MIN_AREA` |
| nodata | **障壁**（`--nodata-as-water` で切替） | |

刻み 0.05 m は DEM の高さ精度（目安 0.25 m）より細かく、量子化が支配要因にならない範囲。
4 近傍を既定にするのは、8 近傍だと 1 セルの対角隙間を水が通り、0.5 m 格子では
過大評価しやすいため。

**seed の決め方**: 標高が閾値以下、または nodata のセルを候補とし、
そのうち**配列の外周に接し**、面積が最小面積以上の連結成分を開放水面とする
（AOI の外の海・水路に通じているもの）。選ばれた成分の面積・重心・nodata 率を
メタデータに残す。**高解像度地形から 1 度だけ求め、粗グリッド用に集約して全条件で共有する。**

nodata を自動的に水にしないのは、京都府 DEM の nodata が主に開放水面である一方、
建物跡の欠測も混ざりうるため。

```
seed セルは標高 -inf 扱い（常に水位 H の水がある開境界）
h_conn = +inf の配列
for H in arange(H_min, H_max + dH, dH):        # 昇順
    cand = passable & (E <= H)
    lab, n = scipy.ndimage.label(cand, structure=conn)
    seed_labels = 非ゼロの lab[seed & cand]
    newly = isin(lab, seed_labels) & isinf(h_conn)
    h_conn[newly] = H
```

出力は `h_conn_{condition}.tif`（Float32、到達しないセルは nodata）。

## 比較

`scripts/40_compare.py`。粗い条件を 0.5 m 格子に**最近傍**でリサンプルする
（双線形にすると粗地形に無い滑らかさを与えてしまう）。

比較する組は 5 つ:
`baseline↔highres` / `control↔highres` / `baseline↔control` /
`highres↔pointcloud` / `baseline↔pointcloud`。

代表水位（1.0 / 1.5 / 2.0 m T.P.）ごとに浸水面積・入れ替わり面積・浸水深差の分布を出し、
`changed(H)` をポリゴン化する。全水位一括の指標として `Δh_conn` を出す。
正なら「高解像度ではより高い水位でないと浸からない」（微地形の峰が守っている）、
負なら「粗地形が見落とした低い経路がある」。

## 地物との結合

`scripts/50_join_semantics.py`。PLATEAU `bldg` / `tran` を lxml の iterparse で読み、
EPSG:6674 のポリゴンにする。

**建物**: `bldg:lod0RoofEdge`（屋根外形 = footprint）を使い、集計ゾーンは
**footprint の外周 1.0 m バッファのリング**（内部は使わない）。

**道路**: `tran:Road` の `lod1MultiSurface` をそのままゾーンにする。

| 量 | 取り方 |
|---|---|
| `ground_elev` | ゾーン内の標高の **10 パーセンタイル**（最低値は外れ値に弱い） |
| `h_conn` | ゾーン内の `h_conn` の**最小値** |
| `water_fraction` | ゾーンに占める開放水面セルの割合 |

**除外の規則**: `uro:RoadStructureAttribute.sectionType` が
高架橋・橋梁・トンネル・アンダーパスのもの、または `water_fraction > 0.5` のものを
`unreliable` として集計から外す（理由も列に残す）。

**判定**: 浸水深は `h_conn <= H` かつ `H > ground_elev` のときだけ `H - ground_elev`。
判定が変わったかは、建物は「浸水するかどうかの入れ替わり」、
道路は**通行支障クラスの変化**で見る。クラス閾値は 0.1 / 0.3 / 0.5 m。

**閾値 0.1 / 0.3 / 0.5 m の位置づけ [既知]**。全国の道路管理者がアンダーパス等で
使う運用値とほぼ一致する — 冠水深 **5 cm 前後で通行注意・15 cm で通行止め**
（香川県・兵庫県ほか、着色板の表示規則）、乗用車は **30 cm で走行困難・50 cm で
浮上**、ドア下端を超えると車内浸水・車外水圧でドアが開かない（JAF ユーザーテスト、
国交省リコール情報）。**いずれも運用値であって技術基準ではない** — 根拠を明記した
公的文書は見つかっていない。数字自体は `config.py` の `ROAD_DEPTH_CLASSES` が
catalog 経由でブラウザに渡るので、画面側には書かない。

**ただし舞鶴の高潮では、規制の根拠は「車が通れるか」ではない [既知]**。舞鶴市
建設部土木課は、冠水路について (1) **車両の塩害**（海水で錆・電装トラブル）
(2) **走行波が沿道家屋に被害**（ガラス破損・床下浸水被害の増大）を理由に、
**迂回 → 徐行 → 通行規制** の 3 段で対応している（「高潮や豪雨などで道路が
冠水したときは迂回や徐行をお願いします」<https://www.city.maizuru.kyoto.jp/0000009894.html>）。
どちらも深さの閾値以前に「冠水しているか」と「沿道に家屋があるか」で決まる話で、
通行支障クラスとは別の指標になる。viewer 側の扱いは `docs/todo.md`。

1 行 = 1 地物で `objects.geojson`（Web が読む）と `objects.csv`（検証用）を出す。
4 条件それぞれの `ground_elev` / `h_conn` を持たせているので、
**ブラウザ側は任意の H について判定を再計算できる。**

# 設計から変わった点

実装して分かったことのうち、当初の設計と違っていたもの。

- **入力が 1 ファイルで足りると思い込むと欠測する。** PLATEAU `dem` は AOI が
  3 次メッシュ象限の境界をまたぐため 2 ファイル、京都府 DEM も 1/50000 図郭
  `06LC` / `06MC` の境界をまたぐため 4 タイル必要だった。
- **seed は「与えられたポリゴン」ではなく「外周に接する低標高の連結成分」にした。**
  当初は開放水面のポリゴンを設定で与える想定だったが、京都府 DEM では海域が nodata で、
  手で描いた境界より「外周に接し、面積が一定以上」という規則のほうが再現性が高かった。
  選ばれた成分はメタデータに残すので、暗黙にはならない。
- **地盤高の集計から開放水面セルを除外する処理**と、
  `sectionType` による橋梁・高架橋・トンネルの除外を足した。
  これが無いと橋の上の道路が「水面標高の地盤」として偽陽性の上位に並ぶ。
- **差の主因は解像度ではなくデータ源だった**（`docs/results.md`）。当初の見立てと逆。
- **地形条件は 3 つで始めて 4 つになった。** 実点群を得たあと、
  `pointcloud`（DEM に地上点群の地表面を融合）を 4 つ目として足した。
  当初は「点群が届いたら `highres` を差し替える」つもりだったが、
  **被覆が AOI の一部しかないので置き換えは成立しない。** 融合して別条件にするほうが、
  「点群が何を変えたか」を差分として取り出せる。
