# WEB_RESULTS — 配信性能の実測

`docs/WEB_DESIGN.md` の設計を実装し、**実配信（Cloudflare）に対して cold cache で計測**した結果。

- 配信先: `https://iwagaki-viewer.tonbo.workers.dev`
- 再現: `cd web && BASE=<URL> node perf/run.mjs`
- 生データ: `web/perf/results/*.json`（git 管理外）
- 環境: macOS / Chromium (Playwright, **headed**) / ビューポート 1100×750 / HTTP/2

プラットフォーム側の挙動（Range・圧縮・キャッシュ階層）は `docs/PLATFORM.md`。
残タスクは `docs/TODO.md`。

## 計測の方針

**FPS は指標にしない。** 測るのは「いつ・何バイトで・何が見えたか」。

| マイルストーン | 定義 |
|---|---|
| `first_meaningful_render` | 視野を覆う最小ズーム（z14-15）の terrain + h_conn タイルが GPU に乗り、**浸水色が 1 フレーム描かれた**時刻。高ズームの到着は待たない |
| `time_to_terrain` | 細メッシュ（z16-18）が視野を満たした時刻 |
| `time_to_plateau` | `Tileset3D.isLoaded()` が真になった時刻。**全タイルの取得完了ではない**（視野外まで待つと 49 秒かかる） |
| `time_to_first_useful_pc` | **LOD がその視点に必要と判断した点数の 50 %** が常駐した時刻 |
| `time_to_pc_refined` | 選ばれたノードが出揃った時刻 |

`time_to_first_useful_pc` は当初「常駐 20 万点」という絶対値だったが、
データ密度と LOD 予算を変えるたびに意味が変わるため割合に改めた。
**旧定義の値とは比較できない。**

### ネットワークプロファイル

本リポジトリ定義（DevTools のプリセットそのものではない）。

| profile | down | up | RTT | 用途 |
|---|---|---|---|---|
| `normal` | 無制限 | 無制限 | 0 ms | 上限 |
| `fast4g` | 4 Mbps | 3 Mbps | 70 ms | 一般的なモバイル |
| `slow-highrtt` | 1 Mbps | 0.5 Mbps | 400 ms | **細い回線。想定する最悪** |
| `fatpipe-highrtt` | 20 Mbps | 5 Mbps | 400 ms | 帯域は十分だが RTT が大きい。**往復回数の影響を帯域から切り離す** |

12 秒の計測窓で切る。窓内に到達しなかったものは「—」で、**それ自体が結果**である。

## プロファイル別の実測

配信物: タイル 9.21 MB / 3D Tiles 6.35 MB / 点群 COPC 272 MB / geojson 0.66 MB。

| profile | FMR | terrain | PLATEAU | 点群 useful | shell | 10 秒転送 | req | 並列 peak |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| normal | 1,239 ms | 2,172 ms | 5,777 ms | 2,745 ms | 0.80 MB | 5.18 MB | 59 | 11 |
| fast4g | **876 ms** | 2,661 ms | 7,383 ms | 4,383 ms | 0.80 MB | 4.50 MB | 58 | 11 |
| slow-highrtt | **3,173 ms** | — | — | — | 0.58 MB | 0.91 MB | 21 | 11 |
| fatpipe-highrtt | 1,012 ms | 2,681 ms | 6,788 ms | 4,008 ms | 0.80 MB | 5.18 MB | 59 | 11 |

読み取れること。

1. **progressive loading は成立している。** `fast4g` では 0.88 秒で浸水図が出る。
   PLATEAU も点群も来ていないが、「解析結果は全ロードを待たずに表示する」は満たしている。
2. **`slow-highrtt` は 12 秒で細メッシュに届かない。** 10 秒で 0.91 MB は帯域上限そのもの。
   ここは設計ではなく物量の問題である。
3. **同時実行は 11 で頭打ち。** `nextHopProtocol` から h2 を検出して上限を切り替える経路が効いている。
4. **水位スライダ 31 段の掃引で発行リクエスト 0。** `h_conn` を 1 枚のテクスチャに持ち、
   シェーダの uniform だけ書き換える設計の狙いどおり。

`normal` の FMR が `fast4g` より遅く出ることがある。**回線が空いている条件では
edge のキャッシュ状態と実回線の変動のほうが大きい。** 1 回の測定で順位を読まないこと。

## 転送の内訳

**バイトはデコード後ではなく wire（回線を流れた量）で数える。**
br が効くアセットでは 6 倍ずれる。

`normal` の 10 秒間（合計 5.18 MB）:

| クラス | req | decode 後 | **wire** | 内容 |
|---|---:|---:|---:|---|
| （shell） | 10 | — | **799 kB** | JS / CSS / HTML。**Scheduler を通らない** |
| plateau | 23 | 3,171 kB | **3,155 kB** | b3dm（Draco 済み。圧縮の余地が無い） |
| terrainFine | 25 | 743 kB | 743 kB | PNG（圧縮の余地が無い） |
| pcCoarse | 1 | 141 kB | 141 kB | 点群 |
| pcIndex | 3 | 117 kB | 117 kB | COPC の octree 索引 |
| semantics | 1 | 662 kB | **109 kB** | `objects.geojson`。br で 6.1 倍 |
| terrainCoarse | 4 | 73 kB | 73 kB | PNG |
| prefetch | 1 | 118 kB | **24 kB** | 点群の被覆輪郭 |
| catalog | 1 | 10 kB | **4 kB** | |

`slow-highrtt` の 12 秒で運べた 0.91 MB の内訳は
**shell 585 kB + 地形 319 kB + catalog 4 kB** で、それ以外は 1 バイトも届かない。

> **細い回線で最も大きいのはアプリのコードである。** 地理データではない。
> 優先度制御でこの領域は動かせない（後述）。

### 初期チャンクの内訳

`index-*.js` をソースマップからパッケージ別に集計（minify 前のソース量、計 3.38 MB）:

| パッケージ | ソース量 | 比率 |
|---|---:|---:|
| **maplibre-gl** | **1,057 kB** | **31 %** |
| @deck.gl/core | 548 kB | 16 % |
| @luma.gl/webgl | 354 kB | 10 % |
| @luma.gl/core | 215 kB | 6 % |
| @math.gl/core | 215 kB | 6 % |
| @deck.gl/layers | 194 kB | 6 % |
| @luma.gl/shadertools | 136 kB | 4 % |
| @luma.gl/engine | 118 kB | 3 % |
| （アプリ本体） | **61 kB** | 2 % |

**アプリ本体は 61 kB しかない。** 初期チャンクの正体はライブラリで、その 3 割が maplibre-gl。
そして本プロジェクトの MapLibre は**ベースマップのソースを 1 つも持っていない**
（`view/map.ts` のスタイルは背景色 1 レイヤのみ）。使っているのはカメラ操作・投影・
ナビゲーションコントロール・attribution だけである。

### b3dm の 70 % は使っていない属性だった

実配信の HAR を分解したところ、b3dm 1 枚（2.34 MB）の内訳は:

| | バイト |
|---|---:|
| batch table JSON（PLATEAU の全属性） | **1,645,322（70 %）** |
| batch table BIN | 36,034 |
| glTF（Draco 圧縮済み。頂点はここ） | 657,048 |

中身は水系別の洪水浸水想定区域、土砂災害リスク、`uro:BuildingDetailAttribute_*` を含む
約 70 キーで、**viewer は 1 つも読んでいない**。読むのは `gml_id` と塗り分け用の
`bldg:class` / `bldg:usage` の 3 キーだけ。

`scripts/82_build_plateau_subset.py` の `trim_batch_table()` で切り出し時に絞った。
glTF チャンクはバイト列のまま移すのでジオメトリも見た目も変わらない。

**初回転送 15.5 MB → 8.0 MB。** 残したキーは `3dtiles_report.json` の
`batch_table_keys` に出るので、`buildingColor.ts` と食い違ったら分かる。

## 点群の配信

COPC は **272 MB のファイルだが、運ぶのは必要なノードだけ**である。

| | |
|---|---:|
| 配信物 | 272,359,780 B / 3,753 万点 / 1,594 ノード |
| 既定の視点で運ぶ量 | **258 kB**（pcIndex 117 kB + pcCoarse 141 kB） |
| 常駐 | 12,174 点 / GPU 183 kB / draw call 1 |

**ファイルの 0.1 % しか運んでいない。** それでも歩いた帯は画面ではっきり見える。

### hierarchy は 1 リクエストで取る

COPC の octree 索引は「1 ページ読む → 子ページの位置が分かる → また読む」という
**依存チェーン**で、素朴に辿ると往復回数がそのまま待ち時間になる。

| | 33 ページを辿る | **EVLR を一括** |
|---|---:|---:|
| リクエスト | 33 | **3** |
| 転送量 | 0.20 MB | 0.20 MB |
| index 完了（normal） | 14,608 ms | **4,013 ms** |
| index 完了（fatpipe-highrtt） | 22,212 ms | **3,713 ms** |

**帯域 20 Mbps でも 22 秒かかっていた。** 運んでいるのは 0.20 MB なので帯域の問題ではない。

仕様上、hierarchy の全ページは `user_id='copc'` / `record_id=1000` の EVLR 1 個に
連続して入っている。そこを 1 リクエストで取り、以後はメモリから切り出す。
**転送量は変わらず、往復だけが消えた。**
EVLR が見つからない場合や 8 MB を超える場合はページ単位取得に戻す。

### LOD はカメラに追従する

`selectNodes` は「カメラからノードまでの距離」から画面上の点間隔（screen-space error）を
求め、2 px を下回るノードを落とす。加えて視野の外接矩形で絞る。

| カメラ | LOD が選ぶ点数 |
|---|---:|
| zoom 18.4（寄り） | 546,804 |
| zoom 12.5（引き） | **12,174** |

常駐点数の上限は **60 万点**。deck.gl `PointCloudLayer` の描画コストは点数にほぼ線形で
**約 23 ns/点/frame** なので、300 万点ではドラッグ中 68〜82 ms（12〜15 fps）になる。
60 fps を保てる上限として実測から決めた。

| 常駐点数 | draw call | ドラッグ中 frame p50 |
|---:|---:|---:|
| 2.97 M | 75 | 68〜82 ms |
| 2.13 M | 54 | 57 ms |
| 0.59 M | 15 | **17.9 ms** |

**バイト予算（`帯域推定 × 6`、下限 2 MB）は既定の視点では効いていない。**
2 MB / 8 MB / 40 MB / 既定 の 4 条件を交互に測っても、
転送 141 kB・常駐 12,174 点で完全に同一だった。効くのは寄った時だけである。

デコードは Worker プール（`min(4, cores-2)`）で回すのでメインスレッドは止まらない。
GPU アップロードは 0.3 ms 程度で、ボトルネックではない。

## スケジューリング

すべての取得は 1 つの `Scheduler` を通る（`web/src/net/scheduler.ts`）。

### 優先度クラスと並列上限

| クラス | 優先度 | 群 | 内容 |
|---|---:|---|---|
| `catalog` / `terrainCoarse` | 0 | a | 入口と粗メッシュ。FMR を決める |
| `terrainFine` / `pcIndex` | 1 | b | 細メッシュと COPC 索引 |
| `semantics` / `plateau` | 2 | c | 地物と建物 |
| `pcCoarse` | 3 | d | 点群の粗ノード |
| `pcFine` | 4 | d | 点群の細ノード |
| `prefetch` | 5 | e | 先読み |

`pcCoarse` / `pcFine` は **FMR が立つまで発行しない**。
群ごとの同時実行上限は h2 で a:6 / b:6 / c:4 / d:6 / e:2、全体 12。
HTTP/1.1 を検出したら 4/4/3/3/1、全体 6 に切り替える。

HTTP/1.1 との比較（`fatpipe-highrtt`）では、**多数の小さいタイルを取る terrain フェーズ
だけが 1.2 秒遅い**（2,768 → 3,976 ms）。FMR と PLATEAU は差が出ない。

### キャンセル

視野から外れた要求を切る。切ってよい条件は 3 つすべてを満たすときだけ:

1. 発行時より epoch が進んでいる
2. `stillNeeded()` が偽（= いま必要とされていない）
3. 受信が 8 割未満（8 割超なら捨てるほうが損）

実測（被覆外へ絶対座標で跳ぶシナリオ）:

| profile | cancelled | 内訳 | 無駄バイト |
|---|---:|---|---:|
| normal | 3 | pcFine 3 | 0 |
| fast4g | 35 | terrainFine 34 / pcCoarse 1 | **30.0 kB** |
| fatpipe-highrtt | 34 | terrainFine 33 / pcCoarse 1 | **490.5 kB** |

`fatpipe-highrtt` の 490.5 kB は 1.3 MB の要求を約 38 % 受信した時点で中断したもの。

### range coalescing

LOD が選んだノードを `pointDataOffset` でソートし、gap < 64 KiB・合計 ≤ 4 MiB なら
1 本の Range にまとめる。COPC のノードはファイル上でほぼ連続して並ぶため、
**まとめても「読むが使わないバイト」は 0** である。

まとめた range は**届いた分から順にノード単位でデコードする**
（`FetchTask.parts` / `onPart`）。1 本の完了を待つと、まとめたことが
そのまま「最初の点の遅延」になる。

**効果は確認できていない。** 実点群（1,594 ノード）で on/off を交互に 3 往復した結果:

| profile | 指標 | off | on |
|---|---|---|---|
| normal | pc useful | 1,846 ms (1304–4556) | 1,667 ms (1142–2506) |
| fast4g | pc refined | 9,275 ms (9254–10800) | **10,105 ms (10023–12035)** |
| fatpipe-highrtt | pc useful | 4,752 ms (4707–6906) | 4,286 ms (4252–6761) |

**符号が一定しない。** ノード数は桁で増えたが、LOD 予算では選ばれるノードが
4〜15 本しかなく、まとめられるのは 11〜12 本止まりで機構がほとんど働いていない。
`extraBytes = 0` で無損失なので既定 ON のままにしているが、**効果があるとは書けない。**
`?coalesce=0` で無効化できる。

飛び地の結合はできない。R2 がマルチレンジを受け付けないため（`docs/PLATFORM.md`）。

## 効果が確認できなかった施策

**細い回線で重いレイヤ（PLATEAU / 点群）を地形完了まで後回しにする。**

`?defer=0/1` で交互に 3 往復した結果、**どこにも改善が無く、
`fatpipe-highrtt` では PLATEAU が +42 % 悪化した**（6,691 → 9,517 ms）。
実装は Scheduler の `hold` / `release` 機構ごと撤回した。

前提が間違っていた。1 Mbps では **PLATEAU が 12 秒の窓の中で 1 リクエストも
発行されていない**。取り合う相手がいないので、譲らせても空くものが無い。

`slow-highrtt` の 0.91 MB のうち 585 kB は shell である。
**細い回線への打ち手は初期チャンクの削減であって、優先度制御ではない。**

## 正しさの検証

性能とは別に、**画面に出ている値がオフライン解析と一致するか**を検査する。

| 道具 | 検査する対象 | 結果 |
|---|---|---|
| `web/test/parity.test.mjs` | タイルの RGBA パッキング往復、地物 120 件 × 水位 3 点の `depth` と `decision_changed` が Python 側と一致するか | **1,564 チェック / 0 失敗** |
| `web/test/camera.test.mjs` | カメラ → ローカル座標の換算（純関数） | **11 件 / 0 失敗** |
| `scripts/84_validate_tiles.py` | 焼いたタイルの値の往復 | 24 タイル / 0 失敗 |
| `web/perf/tileorient.mjs` | **画面の画素**と焼いたタイルの同じ座標の値が一致するか | 一致率 **97.3〜97.6 %** |

`parity` と `84` は「タイルの**値**が正しいか」しか見ない。
**「その値が画面のどこに出ているか」**は `tileorient.mjs` が見る。

### 見つかった描画の誤り

いずれも**絵を見ても気づけない**種類で、値の検査では捕まらなかった。

| 誤り | 内容 | ずれ量 |
|---|---|---|
| 南北反転 | タイルは 1 行目が北。uv は `v=0` が南。反転せずに引いていた | **タイルの高さそのもの**（z15 で 1.2 km） |
| 半セルずれ | タイルは area-registered（1 画素 = 1 セル、中心は `(k+0.5)/256`）。point-registered として引いていた | ズーム依存（z15 1.95 m / z18 0.24 m） |
| 法線の符号 | y 成分が逆。反転したサンプルと打ち消し合って**陰影だけそれらしく見えていた** | — |

南北反転を直して一致率 **78.7 % → 97.3〜97.6 %**、
標高が H±0.25 m の画素と汀線 1 セルを除けば **99.6〜100.0 %**。

`tileorient.mjs` には**視差の補正が要る**。`map.unproject` は z=0 平面との交点を返すが、
地表は `geoid 36.955 m + 標高` の高さに描かれている。zoom 17 のカメラ高度は 510 m なので
**7.2 %（画面端で 41 px）外側**に写る。これを入れないと、汀線の食い違いが
「向きのずれ」なのか視差なのか分けられない。

残る 2.7 % は標高が H の前後にある画素に集中する。メッシュは 128 分割で
テクスチャは 256 なので、水深は **2 分の 1 に間引いた標高**から作られる。
吉原は起伏 0〜3 m で H=1.0 m がその真ん中なので、ここが動く。

## 計測時の注意

いずれも**実際に間違えて結論を出しかけた**もの。

### headed で測る

headless では requestAnimationFrame が絞られ、deck.gl の再描画がほとんど走らない。
`Tile3DLayer` の traversal は再描画のたびにしか進まないので、
**再描画駆動の指標がすべて実際より悪く出る。**

| | headless | headed |
|---|---|---|
| PLATEAU タイル（25 秒） | 13 / 22 | **22 / 22** |
| `time_to_plateau` | 立たない | **3,317 ms** |
| traversal frame 数 | 11 | **29** |

fetch 駆動の指標（FMR・転送バイト・往復回数）は影響を受けない。
歪むのは `time_to_plateau` / `pc refined` / LOD の選択 / カメラ settle。

### 1 回で判断しない

絞りなしでも `time_to_terrain` は **478〜992 ms** の幅を持つ。
A/B は `perf/ab.mjs` で**交互に**複数回まわし、中央値と範囲を見る。
交互にするのは時間帯による回線変動を両条件に等しく乗せるため。

### 転送量は wire で見る

デコード後のバイト数を数えると、br が効くアセットで大きくずれる。

| | decode 後 | wire | 比 |
|---|---:|---:|---:|
| `objects.geojson` | 662 kB | **109 kB** | 6.1× |
| 点群被覆の輪郭 | 118 kB | **24 kB** | 4.8× |
| b3dm・PNG | — | ほぼ等しい | 1.0× |

`fetch` のヘッダからは取れない（`docs/PLATFORM.md`）ので、
`PerformanceResourceTiming.encodedBodySize` を URL と開始時刻で引き当てる。
引き当てられない場合は**デコード後の値に戻す**。過大に出る方に倒す。
小さく見せる方に倒すと判断を誤る。

**帯域推定にも同じ値を使うこと。** デコード後で数えていたときは帯域を 6 倍に
見積もっており、点群の LOD 予算がその分だけ甘くなっていた。

### 0 件を結果として受け入れない

キャンセルが 0 件でも「たまたま切る場面が無かった」で説明がついてしまう。
実際には機構が壊れていた（epoch のカウンタが別物 / LOD がカメラを見ていない /
reap が LOD の更新より先に走る、の 3 つが重なっていた）。
**機構が動いていることを別途確かめる。**

### 計測ハーネス自体も検証対象

`--suffix=?pc=1` を `split('=')[1]` で読んでいて `?pc` に化けており、
点群ありのつもりの計測が点群なしになっていた。**出た数字をそのまま信じない。**

## この計測の限界

1. **AOI が 1 km 四方**しかない。市域全体を載せたときの負荷とは違う。
2. **1 拠点からの測定**。日本国内・固定回線からで、地理的な RTT 分布は入っていない。
3. **edge キャッシュが温まった状態（`cf-cache-status: HIT`）は測っていない。**
   COPC はそもそも CDN に乗らない（`docs/PLATFORM.md`）。
4. **カメラ操作シナリオが 2 種類**（水位掃引 / 被覆外へ跳ぶ）しかない。
