# WEB_RESULTS — 配信性能の実測

`docs/web_design.md` の設計を実装し、**実配信（Cloudflare）に対して cold cache で計測**した結果。

- 配信先: `https://iwagaki-viewer.tonbo.workers.dev`
- 再現: `cd web && BASE=<URL> node perf/run.mjs`
- 生データ: `web/perf/results/*.json`（git 管理外）
- 環境: macOS / Chromium (Playwright, **headed**) / ビューポート 1100×750 / HTTP/2

プラットフォーム側の挙動（Range・圧縮・キャッシュ階層）は `docs/platform.md`。
残タスクは `docs/todo.md`。

## 計測の方針

**FPS は指標にしない。** 測るのは「いつ・何バイトで・何が見えたか」。

| マイルストーン | 定義 |
|---|---|
| `first_meaningful_render` | 視野を覆う最小ズーム（z14-15）の terrain + h_conn タイルが GPU に乗り、**浸水色が 1 フレーム描かれた**時刻。高ズームの到着は待たない |
| `time_to_terrain` | 細メッシュ（z16-18）が視野を満たした時刻 |
| `time_to_plateau` | `Tileset3D.isLoaded()` が真になった時刻。**全タイルの取得完了ではない**（視野外まで待つと 49 秒かかる） |
| `time_to_first_useful_pc` | **LOD がその視点に必要と判断した点数の 50 %** が常駐した時刻 |
| `time_to_pc_refined` | 選ばれたノードが出揃った時刻 |

`time_to_first_useful_pc` は当初「常駐 20 万点」という絶対値だったが、
データ密度と LOD 予算を変えるたびに意味が変わるため割合に改めた。
**旧定義の値とは比較できない。**

### ネットワークプロファイル

本リポジトリ定義（DevTools のプリセットそのものではない）。

| profile | down | up | RTT | 用途 |
|---|---|---|---|---|
| `normal` | 無制限 | 無制限 | 0 ms | 上限 |
| `fast4g` | 4 Mbps | 3 Mbps | 70 ms | 一般的なモバイル |
| `slow-highrtt` | 1 Mbps | 0.5 Mbps | 400 ms | **細い回線。想定する最悪** |
| `fatpipe-highrtt` | 20 Mbps | 5 Mbps | 400 ms | 帯域は十分だが RTT が大きい。**往復回数の影響を帯域から切り離す** |

12 秒の計測窓で切る。窓内に到達しなかったものは「—」で、**それ自体が結果**である。

（`decode.worker` と `laz-perf.wasm` は 4 本の Worker がそれぞれ取る）。
転送量は CDP の `Network` イベントで数えた下記「描画層を替えて〜」の表を見ること。

既定視点を点群の帯（17.2）に寄せたあとの実測は次節。

読み取れること。

1. **progressive loading は成立している。** `fast4g` では 0.82 秒で浸水図が出る。
   PLATEAU も点群も来ていないが、「解析結果は全ロードを待たずに表示する」は満たしている。
2. **`slow-highrtt` は 12 秒で細メッシュに届かない。** ここは設計ではなく物量の問題である。
3. **FMR は全プロファイルで縮んだ**（normal・fast4g・slow・fatpipe いずれも）。
   `fatpipe-highrtt` では PLATEAU も 6.4 秒 -> 5.2 秒。
4. **`fast4g` だけ PLATEAU と点群が 12 秒窓から外れた**（7.4 秒 -> 窓外、4.4 秒 -> 窓外）。
   **これは three.js が遅いからではない。** b3dm の要求開始はむしろ 1.1 秒早い
   （3,799 ms -> 2,658 ms）。原因は次項の LOD で、**旧実装が点群をほとんど
   読んでいなかった**ためである。

### 既定の視点で点群 LOD が最粗に張り付いていた **[実測]**

同じ既定視点で `wantedPoints` を比べると:

| | wantedPoints |
|---|---:|
| MapLibre + deck.gl | **12,174** |
| three.js | **124,550** |

**12,174 は「引き切ったとき」の値と同じ**（下の LOD の表を見よ）。つまり旧実装は
既定視点でも最粗のノード集合しか選んでいなかった。

原因は `domain/camera.ts` の `metresPerPixel(lat, zoom)` で、
式は 256 px タイル基準（定数 156543.03392 = 2πR/256）なのに、
**MapLibre の 512 px 基準の `getZoom()` を渡していた**。カメラ距離が常に 2 倍になり、
screen-space error が 1/2 に見えていた。three.js の `getZoom()` は 256 px 基準なので、
移行と同時に正しくなった。

したがって `fast4g` の PLATEAU 到達が遅れたのは**点群を 10 倍読むようになった結果**で、
帯域の取り合いである。**「LOD を細い回線向けに浅く止める」（`docs/todo.md`）は、
これで初めて実測できる問題になった。**
3. **同時実行は 11 で頭打ち。** `nextHopProtocol` から h2 を検出して上限を切り替える経路が効いている。
4. **水位スライダ 31 段の掃引で発行リクエスト 0。** `h_conn` を 1 枚のテクスチャに持ち、
   シェーダの uniform だけ書き換える設計の狙いどおり。

`normal` の FMR が `fast4g` より遅く出ることがある。**回線が空いている条件では
edge のキャッシュ状態と実回線の変動のほうが大きい。** 1 回の測定で順位を読まないこと。

## 転送の内訳

**バイトはデコード後ではなく wire（回線を流れた量）で数える。**
br が効くアセットでは 6 倍ずれる。

`normal` の 10 秒間（合計 5.18 MB）:

| クラス | req | decode 後 | **wire** | 内容 |
|---|---:|---:|---:|---|
| （shell） | 10 | — | **799 kB** | JS / CSS / HTML。**Scheduler を通らない** |
| plateau | 23 | 3,171 kB | **3,155 kB** | b3dm（Draco 済み。圧縮の余地が無い） |
| terrainFine | 25 | 743 kB | 743 kB | PNG（圧縮の余地が無い） |
| pcCoarse | 1 | 141 kB | 141 kB | 点群 |
| pcIndex | 3 | 117 kB | 117 kB | COPC の octree 索引 |
| semantics | 1 | 662 kB | **109 kB** | `objects.geojson`。br で 6.1 倍 |
| terrainCoarse | 4 | 73 kB | 73 kB | PNG |
| prefetch | 1 | 118 kB | **24 kB** | 点群の被覆輪郭 |
| catalog | 1 | 10 kB | **4 kB** | |

`slow-highrtt` の 12 秒で運べた 0.91 MB の内訳は
**shell 585 kB + 地形 319 kB + catalog 4 kB** で、それ以外は 1 バイトも届かない
（MapLibre + deck.gl のとき）。

> **細い回線で最も大きいのはアプリのコードである。** 地理データではない。
> 優先度制御でこの領域は動かせない（後述）。

これが three.js への置き換えの直接の動機である。置き換え後は
**shell 212 kB + 地理データ 820 kB**（12 秒）になった（上記「描画層を替えて〜」）。

### 描画層を替えて細い回線で何が変わったか **[実測]**

`slow-highrtt`（1 Mbps / RTT 400 ms）、同一データ・同一ビューポート・
**同一の可視範囲と同一の要求タイル**（後述「ズームの基準を取り違えていた」）で
3 回ずつ。ばらつきは 2 % 未満。

| 指標 | MapLibre + deck.gl | three.js | 差 |
|---|---:|---:|---|
| shell バイト（地理データ前） | 574,146 B / 5 req | **212,290 B / 3 req** | **−63.0 %** |
| バンドル取得 + 実行 | 4,809 ms | **2,060 ms** | **−57.2 %** |
| **FMR（ナビゲーション基準）** | 7,739 ms | **4,940 ms** | **−2.80 s（−36.2 %）** |
| terrain 完了（ナビ基準） | 15,319 ms | 13,615 ms | −1.70 s（−11.1 %） |
| **地理データ @10 s** | 313,640 B | **548,320 B** | **+74.8 %** |
| 地理データ @12 s | 536,782 B | **819,634 B** | +52.7 % |

**12 秒の窓に入る地理データが 1.5〜1.75 倍になった。** これが「初期チャンクを削る」の
実体である。バイトが小さくなったこと自体ではなく、**空いた帯域が地理データに回ったこと**を見る。

2 つ注意がある。

1. **`first_meaningful_render` は 2 つある。** `recorder.ts` の `t0` は
   **recorder が構築された時刻**、つまりバンドルを落として実行し終えた後である。
   この基準で比べると 3,013 ms 対 3,126 ms で「改善なし」に見える。**shell のコストは
   定義上そこに入っていない。** 比較には `milestones_navigation` を使う。
2. **`perf/shellcost.mjs` の `time_to_canvas_ms` は当てにならない。**
   検出条件が「幅・高さ 100 px 超の canvas」で、`index.html` に静的に置いてある
   断面図の `<canvas id="sec-canvas">`（高さ 200 px）を拾う。MapLibre 側で 0.5 秒と
   出るのはこれで、地図の canvas ではない。

#### 直し方

`scripts/vendor-draco.mjs` が `node_modules/@loaders.gl/draco/dist/libs/` から
`public/vendor/draco@<version>/dist/libs/` に複製し、`options.CDN` をそこへ向ける。
worker は `@loaders.gl/draco/draco-worker.js?url` でバンドルに同梱する。

`options.modules` に URL を直接渡す道は**効かなかった**（worker へ渡る途中で落ちて
既定の CDN に戻る。実測）。パスに loaders.gl のバージョンが入るので `_headers` で
`immutable` にしてよい。

`deploy/check.mjs` に MUST **「外部オリジンへのリクエストが 0 件」**を足した。
ここだけブラウザを立てる。**`fetch` では分からない**（外部を叩くのはライブラリが
動き出してからで、しかも Worker の中から出る）。playwright が無い環境では
**通過にせず MUST を落とす** — 「測っていない」を「通った」と読ませないため。

#### バンドルに残る `unpkg.com` の文字列は発火しない **[実測]**

Draco を自オリジン配信に直したあとも `dist/assets/plateauTiles-*.js` に
`https://unpkg.com/@loaders.gl` が残る。追ったところ **`@loaders.gl/core` の
既定オプション**（`CDN: "https://unpkg.com/@loaders.gl"`, `useLocalLibraries: false`）で、
worker の URL を組み立てるときに使われる文字列だった。発火条件は
「loaders.gl が worker を要求し、かつ `CDN` が既定のまま」。

**呼び出し側で潰してある。** `three/plateauTiles.ts` の `DRACO_LOCAL` が
唯一の `parse()` に `CDN: abs('vendor')` と `draco.workerUrl` を渡すので、
既定値に落ちる経路が無い。`deploy/check.mjs` の「外部オリジンへのリクエストが 0 件」
も毎回通っている。

**文字列そのものを消すには依存の patch が要る**（ライブラリの既定値なので
tree-shake で落ちない）。割に合わないので消さない。
なお `webgl-debug` と `cdn.jsdelivr.net/npm/spectorjs` は
**もうバンドルに無い**（MapLibre を外した時点で消えていた）。

## 点群の配信

COPC は **272 MB のファイルだが、運ぶのは必要なノードだけ**である。

| | |
|---|---:|
| 配信物 | 272,359,780 B / 3,753 万点 / 1,594 ノード |
| 既定の視点で運ぶ量 | **258 kB**（pcIndex 117 kB + pcCoarse 141 kB） |
| 常駐 | 12,174 点 / GPU 183 kB / draw call 1 |

**ファイルの 0.1 % しか運んでいない。** それでも歩いた帯は画面ではっきり見える。

### hierarchy は 1 リクエストで取る

COPC の octree 索引は「1 ページ読む → 子ページの位置が分かる → また読む」という
**依存チェーン**で、素朴に辿ると往復回数がそのまま待ち時間になる。

| | 33 ページを辿る | **EVLR を一括** |
|---|---:|---:|
| リクエスト | 33 | **3** |
| 転送量 | 0.20 MB | 0.20 MB |
| index 完了（normal） | 14,608 ms | **4,013 ms** |
| index 完了（fatpipe-highrtt） | 22,212 ms | **3,713 ms** |

**帯域 20 Mbps でも 22 秒かかっていた。** 運んでいるのは 0.20 MB なので帯域の問題ではない。

仕様上、hierarchy の全ページは `user_id='copc'` / `record_id=1000` の EVLR 1 個に
連続して入っている。そこを 1 リクエストで取り、以後はメモリから切り出す。
**転送量は変わらず、往復だけが消えた。**
EVLR が見つからない場合や 8 MB を超える場合はページ単位取得に戻す。

### LOD はカメラに追従する

`selectNodes` は「カメラからノードまでの距離」から画面上の点間隔（screen-space error）を
求め、2 px を下回るノードを落とす。加えて視野の外接矩形で絞る。

| カメラ | LOD が選ぶ点数 |
|---|---:|
| zoom 18.4（寄り） | 546,804 |
| zoom 12.5（引き） | **12,174** |

#### deck.gl `PointCloudLayer` のとき

描画コストは点数にほぼ線形で **約 23 ns/点/frame**。300 万点ではドラッグ中
68〜82 ms（12〜15 fps）になり、60 fps を保てる上限として **60 万点**を置いていた。

| 常駐点数 | draw call | ドラッグ中 frame p50 |
|---:|---:|---:|
| 2.97 M | 75 | 68〜82 ms |
| 2.13 M | 54 | 57 ms |
| 0.59 M | 15 | **17.9 ms** |

#### three.js `Points` で測り直すと桁が違う **[実測]**

`perf/pcbudget.mjs`、2 回。**p50 は vsync に張り付く（16.7 ms）ので p95 と max も出す。**

| budget | 常駐点数 | draw call | GPU | drag p50 | p95 | max |
|---|---:|---:|---:|---:|---:|---:|
| 12 M | 9.86 / 10.36 M | 209 / 222 | 148 / 155 MB | 16.7 / 16.8 ms | **26.9 / 43.7 ms** | 67.9 / 79.3 ms |
| 6 M | 5.97 M | 132 | 90 MB | 16.6 ms | 18.2 ms | 18.7 ms |
| 3 M | 3.00 M | 65 | 45 MB | 16.7 ms | 18.0 / 18.1 ms | 18.5 / 39.4 ms |
| 1.5 M | 1.46 M | 32 | 22 MB | 16.7 ms | 18.1 ms | 18.5 ms |
| 0.8 M | 0.80 M | 18 | 12 MB | 16.7 ms | 17.4 / 17.9 ms | 18.0 / 18.1 ms |
| 0.3 M | 0.27 M | 7 | 4 MB | 16.6 / 16.7 ms | 17.8 / 17.9 ms | 18.4 ms |

**6.0 M 点まで 60 fps を保つ。** deck.gl が 3.0 M で 68〜82 ms だったところである。
崩れ始めるのは 9.9 M 点（p95 26.9〜43.7 ms）。1 点 1 頂点になった分が素直に出ている。

**測った上限はそのまま採らない。** 計測は開発機（Apple Silicon）で、
配信先の庁内 PC の GPU は分かっていない [未確認]。既定は実測の 1/3 に当たる
**200 万点**（GPU 30 MB）に上げた。3 倍遅い GPU でも 60 fps に収まる計算になる。

**ただし細い回線ではここは効かない。** 既定の視点で LOD が要求するのは 12.5 万点で、
効いているのは `maxBytes`（帯域推定）と screen-space error のほうである。

**バイト予算（`帯域推定 × 6`、下限 2 MB）は既定の視点では効いていない。**
2 MB / 8 MB / 40 MB / 既定 の 4 条件を交互に測っても、
転送 141 kB・常駐 12,174 点で完全に同一だった。効くのは寄った時だけである。

デコードは Worker プール（`min(4, cores-2)`）で回すのでメインスレッドは止まらない。
GPU アップロードは 0.3 ms 程度で、ボトルネックではない。

### 点群 LOD の予算は事実上ただの下限だった **[実測]**

`docs/todo.md`「細い回線向けに点群 LOD を浅く止める閾値」を実測しに行って、
**閾値の式がそもそも働いていない**ことが分かった。予算は
`maxBytes = clamp(bandwidthBps * 6, 2 MB, 20 MB)` だったが:

| profile | 実効帯域 | 旧推定 | 比 | `bw * 6` | 実際の予算 |
|---|---:|---:|---:|---:|---|
| slow-highrtt | 125 kB/s | 11 kB/s | 0.09x | 66 kB | 下限 2 MB |
| fast4g | 500 kB/s | 89 kB/s | 0.18x | 534 kB | 下限 2 MB |
| fatpipe-highrtt | 2.5 MB/s | 276〜374 kB/s | 0.13x | 1.7〜2.2 MB | 下限の境目で揺れる |
| normal | 無制限 | 10.7〜24.3 MB/s | — | 上限超え | 上限 20 MB |

原因は `noteBandwidth()` が **1 リクエストごとに `wireBytes / 所要時間`** を測って
いたこと。11 本並列に走っていれば 1 本あたりは 1/11 に見える。
**測っていたのは回線の容量ではなく 1 接続あたりの速度である。**

### 直したこと **[実測]**

3 つある。**順番に意味がある**（推定が 1/5 しか出ていない状態で係数を調整しても、
合わせているのは誤差のほうになる）。

**1. 推定を「回線全体」に直した。** 直近 4 秒の完了分を合計し、
**その間に実際に取得が走っていた時間**（区間の和集合）で割る。
並列に走った分はここで足し合わされる。待ち時間で割らないのは、
アイドルを挟むと容量を過小に見積もるため。

| profile | 実効帯域 | 旧推定 | **新推定** |
|---|---:|---:|---:|
| slow-highrtt | 125 kB/s | 11 kB/s (0.09x) | **106〜128 kB/s (0.85〜1.02x)** |
| fast4g | 500 kB/s | 89 kB/s (0.18x) | **502 kB/s (1.00x)** |
| fatpipe-highrtt | 2.5 MB/s | 276〜374 kB/s (0.13x) | **1.37 MB/s (0.55x)** |

速い回線ほど低めに出るのは、和集合の中に「1〜2 本しか飛んでいない待ち時間」が
入るため。**過小に倒れるので、予算を甘くする方向には効かない。**
回帰は `perf/bwcheck.mjs` が見る。

**2. 推定が落ち着いたら予算を評価し直す。** それまで `budget()` を評価するのは
点群の起動時とカメラ移動時だけで、**カメラを動かさなければ起動直後の値が最後まで
残っていた**。1 秒ごとに見て、1.5 倍を超えて**増えた**ときだけ組み直す。

**減る方向には組み直さない。** 選び直すと常駐していたノードが捨てられ、
取得済みのバイトが無駄になる。実測（`fast4g`・12 秒窓）で、下げ直すと
転送は 2.88 -> 3.29 MB に増えるのに常駐点数は 68,622 -> 56,448 に減った。
**払って減らしている。** 視野が変わったときは別で、カメラ移動の経路が改めて評価する。

推定がまだ無いときの既定も直した。以前は 2 MB/s と仮定していて、
起動直後の 1 回だけ 6 MB の予算が出ていた。いまは下限から始めて上げていく。

**3. 係数を 6 から 2 にした。** = **「点群に使ってよいのは 12 秒の窓のうち 2 秒ぶん」**。
残りは地形・建物・地物に要る。下限は 2 MB から 1 MB に下げた。

### 直した結果（12 秒窓、2 回）**[実測]**

| profile | | PLATEAU | 建物 | 常駐 / 要求 | @10s |
|---|---|---:|---|---|---:|
| fast4g | 前 | — | 20/22 | 56,448 / 124,550 | 3,291,372 |
| | **後** | — | 20/22 | **68,622 / 68,622（完了）** | **2,882,622** |
| fatpipe-highrtt | 前 | 6,030 ms | 22/22 | 68,622 か 124,550（run ごとに跳ぶ） | 5,935,511 |

**`fast4g` で転送を 409 kB 減らしながら常駐点数が増えた。** 12 秒の窓で取り切れない

`fast4g` の PLATEAU は 12 秒窓に入らないまま（建物 20/22）。予算を 0.5 MB まで

|---|---:|---|---:|

### 視錐台を厳密にしても、この点群では何も落ちない **[実測]**

視野判定は「地面に落とした視錐台の**外接矩形**」だった。傾けるほど広く出るので、
台形そのもので判定するように直した（`domain/camera.ts` の
`visiblePolygonLocal` / `boxIntersectsPolygon`、分離軸判定）。

どれだけ広かったかは `perf/frustum.mjs` が出す:

| 視点 | 台形 | 外接矩形 | 比 | `wantedPoints` |
|---|---:|---:|---:|---:|
| pitch 0 | 1.358 km² | 1.358 km² | **1.00x** | 124,550 |
| pitch 52（既定） | 3.298 km² | 6.046 km² | 1.83x | 124,550 |
| pitch 75 | 9.924 km² | 19.187 km² | 1.93x | 124,550 |
| pitch 84 | 10.042 km² | 19.938 km² | **1.99x** | 124,550 |
| pitch 84・zoom 14.6 | 160.664 km² | 318.979 km² | 1.99x | 12,174 |

**外接矩形は傾けた視野で実際のほぼ 2 倍を「見えている」と答えていた。**
pitch 0 で 1.00 倍になるのが、幾何が正しいことの確認になる。

**それでも選ばれるノードは 1 つも変わらない。** 点群の octree は
**427 x 799 m = 0.34 km²** しかなく、最も狭い pitch 0 の台形（1.36 km²）にも

（`docs/todo.md` の LAS アップロード）ではここが効くこと**。
**いまの配信物に対しては効果ゼロ**であり、そう書いておく。

### `slow-highrtt` では関係ない

1 Mbps では**点群は 12 秒の窓で 1 ノードも要求していない**（`wantedPoints` 0）。
予算を 0.25 MB にしても 2 MB にしても `@10s` は変わらない。
「細い回線への打ち手は初期チャンクの削減であって優先度制御ではない」という
以前の結論（上記「効果が確認できなかった施策」）は、ここでは変わっていない。
**効くのは `fast4g` 帯である。**

## スケジューリング

すべての取得は 1 つの `Scheduler` を通る（`web/src/net/scheduler.ts`）。

### 優先度クラスと並列上限

| クラス | 優先度 | 群 | 内容 |
|---|---:|---|---|
| `catalog` / `terrainCoarse` | 0 | a | 入口と粗メッシュ。FMR を決める |
| `terrainFine` / `pcIndex` | 1 | b | 細メッシュと COPC 索引 |
| `semantics` / `plateau` | 2 | c | 地物と建物 |
| `pcCoarse` | 3 | d | 点群の粗ノード |
| `pcFine` | 4 | d | 点群の細ノード |
| `prefetch` | 5 | e | 先読み |

`pcCoarse` / `pcFine` は **FMR が立つまで発行しない**。
群ごとの同時実行上限は h2 で a:6 / b:6 / c:4 / d:6 / e:2、全体 12。
HTTP/1.1 を検出したら 4/4/3/3/1、全体 6 に切り替える。

HTTP/1.1 との比較（`fatpipe-highrtt`）では、**多数の小さいタイルを取る terrain フェーズ
だけが 1.2 秒遅い**（2,768 → 3,976 ms）。FMR と PLATEAU は差が出ない。

### キャンセル

視野から外れた要求を切る。切ってよい条件は 3 つすべてを満たすときだけ:

1. 発行時より epoch が進んでいる
2. `stillNeeded()` が偽（= いま必要とされていない）
3. 受信が 8 割未満（8 割超なら捨てるほうが損）

実測（被覆外へ絶対座標で跳ぶシナリオ）:

| profile | cancelled | 内訳 | 無駄バイト |
|---|---:|---|---:|
| normal | 3 | pcFine 3 | 0 |
| fast4g | 35 | terrainFine 34 / pcCoarse 1 | **30.0 kB** |
| fatpipe-highrtt | 34 | terrainFine 33 / pcCoarse 1 | **490.5 kB** |

`fatpipe-highrtt` の 490.5 kB は 1.3 MB の要求を約 38 % 受信した時点で中断したもの。

### range coalescing

LOD が選んだノードを `pointDataOffset` でソートし、gap < 64 KiB・合計 ≤ 4 MiB なら
1 本の Range にまとめる。COPC のノードはファイル上でほぼ連続して並ぶため、
**まとめても「読むが使わないバイト」は 0** である。

まとめた range は**届いた分から順にノード単位でデコードする**
（`FetchTask.parts` / `onPart`）。1 本の完了を待つと、まとめたことが
そのまま「最初の点の遅延」になる。

**効果は確認できていない。** 実点群（1,594 ノード）で on/off を交互に 3 往復した結果:

| profile | 指標 | off | on |
|---|---|---|---|
| normal | pc useful | 1,846 ms (1304–4556) | 1,667 ms (1142–2506) |
| fast4g | pc refined | 9,275 ms (9254–10800) | **10,105 ms (10023–12035)** |
| fatpipe-highrtt | pc useful | 4,752 ms (4707–6906) | 4,286 ms (4252–6761) |

**符号が一定しない。** ノード数は桁で増えたが、LOD 予算では選ばれるノードが
4〜15 本しかなく、まとめられるのは 11〜12 本止まりで機構がほとんど働いていない。
`extraBytes = 0` で無損失なので既定 ON のままにしているが、**効果があるとは書けない。**
`?coalesce=0` で無効化できる。

飛び地の結合はできない。R2 がマルチレンジを受け付けないため（`docs/platform.md`）。

## 効果が確認できなかった施策

**細い回線で重いレイヤ（PLATEAU / 点群）を地形完了まで後回しにする。**

`?defer=0/1` で交互に 3 往復した結果、**どこにも改善が無く、
`fatpipe-highrtt` では PLATEAU が +42 % 悪化した**（6,691 → 9,517 ms）。
実装は Scheduler の `hold` / `release` 機構ごと撤回した。

前提が間違っていた。1 Mbps では **PLATEAU が 12 秒の窓の中で 1 リクエストも
発行されていない**。取り合う相手がいないので、譲らせても空くものが無い。

`slow-highrtt` の 0.91 MB のうち 585 kB は shell である。
**細い回線への打ち手は初期チャンクの削減であって、優先度制御ではない。**
実際そのとおりで、shell を 212 kB に落としたら 12 秒窓の地理データが
537 kB から 820 kB になった（上記「描画層を替えて〜」）。

## 正しさの検証

性能とは別に、**画面に出ている値がオフライン解析と一致するか**を検査する。

| 道具 | 検査する対象 | 結果 |
|---|---|---|
| `web/test/parity.test.mjs` | タイルの RGBA パッキング往復、地物 120 件 × 水位 3 点の `depth` と `decision_changed` が Python 側と一致するか | **1,564 チェック / 0 失敗** |
| `web/test/camera.test.mjs` | カメラ → ローカル座標の換算（純関数） | **11 件 / 0 失敗** |
| `scripts/84_validate_tiles.py` | 焼いたタイルの値の往復 | 24 タイル / 0 失敗 |
| `web/perf/tileorient.mjs` | **画面の画素**と焼いたタイルの同じ座標の値が一致するか | 一致率 **97.3〜97.6 %**（three.js 移行後も 97.3 %。判定が紙一重の帯を外すと 100.0 %） |

`parity` と `84` は「タイルの**値**が正しいか」しか見ない。
**「その値が画面のどこに出ているか」**は `tileorient.mjs` が見る。

### 見つかった描画の誤り

いずれも**絵を見ても気づけない**種類で、値の検査では捕まらなかった。

| 誤り | 内容 | ずれ量 |
|---|---|---|
| 南北反転 | タイルは 1 行目が北。uv は `v=0` が南。反転せずに引いていた | **タイルの高さそのもの**（z15 で 1.2 km） |
| 半セルずれ | タイルは area-registered（1 画素 = 1 セル、中心は `(k+0.5)/256`）。point-registered として引いていた | ズーム依存（z15 1.95 m / z18 0.24 m） |
| 法線の符号 | y 成分が逆。反転したサンプルと打ち消し合って**陰影だけそれらしく見えていた** | — |

南北反転を直して一致率 **78.7 % → 97.3〜97.6 %**、
標高が H±0.25 m の画素と汀線 1 セルを除けば **99.6〜100.0 %**。

`tileorient.mjs` には**視差の補正が要る**。`map.unproject` は z=0 平面との交点を返すが、
地表は `geoid 36.955 m + 標高` の高さに描かれている。zoom 17 のカメラ高度は 510 m なので
**7.2 %（画面端で 41 px）外側**に写る。これを入れないと、汀線の食い違いが
「向きのずれ」なのか視差なのか分けられない。

残る 2.7 % は標高が H の前後にある画素に集中する。メッシュは 128 分割で
テクスチャは 256 なので、水深は **2 分の 1 に間引いた標高**から作られる。
吉原は起伏 0〜3 m で H=1.0 m がその真ん中なので、ここが動く。

## 計測時の注意

いずれも**実際に間違えて結論を出しかけた**もの。

### headed で測る

headless では requestAnimationFrame が絞られ、再描画駆動の処理がほとんど走らない。
当時は deck.gl の `Tile3DLayer` の traversal が再描画のたびにしか進まなかった。
three.js の `Viewer` も `requestAnimationFrame` ループなので事情は同じで、
**再描画駆動の指標がすべて実際より悪く出る。**

| | headless | headed |
|---|---|---|
| PLATEAU タイル（25 秒） | 13 / 22 | **22 / 22** |
| `time_to_plateau` | 立たない | **3,317 ms** |
| traversal frame 数 | 11 | **29** |

fetch 駆動の指標（FMR・転送バイト・往復回数）は影響を受けない。
歪むのは `time_to_plateau` / `pc refined` / LOD の選択 / カメラ settle。

### 1 回で判断しない

絞りなしでも `time_to_terrain` は **478〜992 ms** の幅を持つ。
A/B は `perf/ab.mjs` で**交互に**複数回まわし、中央値と範囲を見る。
交互にするのは時間帯による回線変動を両条件に等しく乗せるため。

### 転送量は wire で見る

デコード後のバイト数を数えると、br が効くアセットで大きくずれる。

| | decode 後 | wire | 比 |
|---|---:|---:|---:|
| `objects.geojson` | 662 kB | **109 kB** | 6.1× |
| 点群被覆の輪郭 | 118 kB | **24 kB** | 4.8× |
| b3dm・PNG | — | ほぼ等しい | 1.0× |

`fetch` のヘッダからは取れない（`docs/platform.md`）ので、
`PerformanceResourceTiming.encodedBodySize` を URL と開始時刻で引き当てる。
引き当てられない場合は**デコード後の値に戻す**。過大に出る方に倒す。
小さく見せる方に倒すと判断を誤る。

**帯域推定にも同じ値を使うこと。** デコード後で数えていたときは帯域を 6 倍に
見積もっており、点群の LOD 予算がその分だけ甘くなっていた。

### 0 件を結果として受け入れない

キャンセルが 0 件でも「たまたま切る場面が無かった」で説明がついてしまう。
実際には機構が壊れていた（epoch のカウンタが別物 / LOD がカメラを見ていない /
reap が LOD の更新より先に走る、の 3 つが重なっていた）。
**機構が動いていることを別途確かめる。**

### 計測ハーネス自体も検証対象

`--suffix=?pc=1` を `split('=')[1]` で読んでいて `?pc` に化けており、
点群ありのつもりの計測が点群なしになっていた。**出た数字をそのまま信じない。**

## この計測の限界

1. **AOI が 1 km 四方**しかない。市域全体を載せたときの負荷とは違う。
2. **1 拠点からの測定**。日本国内・固定回線からで、地理的な RTT 分布は入っていない。
3. **edge キャッシュが温まった状態（`cf-cache-status: HIT`）は測っていない。**
   COPC はそもそも CDN に乗らない（`docs/platform.md`）。
4. **カメラ操作シナリオが 2 種類**（水位掃引 / 被覆外へ跳ぶ）しかない。
5. **プロファイル別の表は 1 試行**。順位を読むには足りない。
   A/B が要る比較は `perf/ab.mjs` で複数回まわしている。
6. 12 秒の計測窓で切っている。`slow-highrtt` は窓内に収まらない。
7. **Draco デコーダの CDN URL がバンドルに残っている。** 現行の b3dm は
   Draco 非圧縮なので発火しないが、将来 Draco を使うと
   クロスオリジンになり `transferSize` が 0 になって計測が濁る。
