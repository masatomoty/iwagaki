# 描画層を MapLibre + deck.gl から three.js に置き換える

## 問い

**細い回線（1 Mbps / RTT 400 ms）で、12 秒の窓に入る地理データを増やせるか。**

前日の `2026-08-22-web-shell.md` は「初期チャンクの 31 % が maplibre-gl」という
観察を出したうえで、対処としては現行実装の継続を選んでいた。覆したのは対処の側である。

## 何が分かっていたか

`docs/web_results.md` の実測:

- `slow-highrtt` の 12 秒で運べた 0.91 MB のうち、**585 kB が shell**（アプリのコード）。
  地理データは 319 kB しかない
- 初期チャンク（ソース量 3.36 MB）の内訳は **maplibre-gl 31 % / deck.gl + luma.gl 45 %**、
  **アプリ本体は 120 kB（4 %）**
- 本プロジェクトの MapLibre は**ベースマップのソースを 1 つも持っていない**。
  使っているのはカメラ・投影・操作・ギズモ・attribution だけ
- 優先度制御は測って撤回済み。1 Mbps では PLATEAU が 12 秒の窓で 1 リクエストも
  発行されないので、譲らせても空くものが無い

つまり**細い回線に効く打ち手は初期チャンクの削減しか残っていなかった**。

## 選択肢

| | 内容 | 却下理由 |
|---|---|---|
| A | MapLibre + deck.gl を継続し、遅延読み込みを詰める | 初期チャンクの 96 % がライブラリで、そのうち MapLibre と deck.gl はカメラと描画そのもの。**遅延にできる部分が無い** |
| B | MapLibre を外し deck.gl 単体（`OrbitView`）にする | deck.gl + luma.gl だけで 1.5 MB。**削減幅が足りない**。加えて正射投影の要求（`docs/todo.md`）が deck.gl の geospatial view では満たせていなかった |
| **C** | **描画層を three.js で自前に持つ** | 採用 |

C の前提は「MapLibre と deck.gl から実際に使っている機能が少ない」ことで、
それは上の観察そのものである。書くことになるのは
カメラ・タイルピラミッド・地形シェーダ・3D Tiles の配置・点群の `Points` の 5 つで、
**`CopcIndex` / `LodSelector` / `Scheduler` / `DecodePool` は 1 行も変わらない**
（`docs/web_design.md`「層の分け方」で分離してあった）。

## 結果 **[実測]**

`slow-highrtt`、同一データ・同一可視範囲・同一の要求タイル、3 回ずつ。

| 指標 | MapLibre + deck.gl | three.js |
|---|---:|---:|
| 初期 JS + CSS（br） | 440,839 B | **131,264 B（−70.2 %）** |
| shell バイト | 574,146 B | **212,290 B（−63.0 %）** |
| FMR（ナビゲーション基準） | 7,739 ms | **4,940 ms（−2.80 s）** |
| **地理データ @10 s** | 313,640 B | **548,320 B（+74.8 %）** |

副産物として正射投影（`docs/todo.md` の積み残し）が入り、
deck.gl `TileLayer` のサブレイヤキャッシュに起因する不具合の芽（水位スライダが
効かなくなる類）が構造的に無くなった。

## 代償

- **描画層を自分で保守することになった。** アプリ本体は 120 kB -> 144 kB。
- **計測ハーネスが MapLibre の API に依存していた。** `perf/*.mjs` のうち 5 本
  （`run` / `pccancelprobe` / `zmix` / `sectionshot` / `tileorient`）が
  `map.jumpTo` / `map.project` / `map.unproject` / `map.transform` を使っており、
  `Viewer` 側に同じ意味のメソッドを足して移した。
  **南北反転を捕まえた `tileorient.mjs` を動く状態に保つことをマージの前提条件にした。**
- **ズームの基準が 1 ずれた。** MapLibre はタイル 512 px 基準、three.js 側は 256 px 基準。
  移行直後は 1 段粗い地形を描いていて、最初の実測が比較として成立していなかった
  （`docs/web_results.md`「ズームの基準を取り違えていた」）。
- **出典表示が一度消えた。** MapLibre の `AttributionControl` が担っていた。
  PLATEAU / 京都府 DEM / 気象庁はいずれも表示を求めているので、`#attrib` として持ち直した。

## 移行で初めて見えた問題

`domain/camera.ts` の `metresPerPixel` は 256 px 基準の式なのに、MapLibre の
512 px 基準の zoom を渡していた。カメラ距離が常に 2 倍になり、
**既定の視点でも点群 LOD が最粗（`wantedPoints` = 12,174 = 引き切ったときと同値）に
張り付いていた**。three.js の `getZoom()` は 256 px 基準なので移行と同時に正しくなり、
既定視点で 124,550 点を要求するようになった。

その結果 `fast4g` で PLATEAU と点群が 12 秒窓から外れた。**これは新たに見えるようになった
容量の問題**であって、three.js の遅さではない（b3dm の要求開始はむしろ 1.1 秒早い）。
`docs/todo.md` の「LOD を浅く止める閾値」がこれで初めて実測できる問題になった。
